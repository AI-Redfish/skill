# 核心结论

skill 决定 agent 能不能越用越聪明。

skill 本质上是“知识 + 工具 + 规则”的资源包，用来在运行时按需加载模型外的信息。

因此：

- skill 质量，和 agent 最终效果高度正相关
- skill 不是越多越好，而是越稳定、越可复用越好
- 企业级 agent 一定要考虑 skill 的持续进化机制



# skill 自进化的演进

## 1. 人工手写

最早是人工逐行写 skill。

- 一行行写描述
- 一点点调边界
- 反复改措辞

问题：

- 效率低
- 很依赖个人经验
- 一个好 skill 可能要改很多轮


## 2. AI 辅助生成

后面开始用各种 skill creator，让 AI 帮忙生成 skill。

优点：

- 生成速度快
- 门槛更低
- 用户只要描述想要的功能

问题：

- 只是“生成更快”
- 还不等于“会进化”


## 3. 自动沉淀雏形

进一步会把对话中的信息自动存成 skill。

例如：

- 用户主动让 agent 创建 skill
- 识别用户画像信息后自动存储
- 每轮任务后自动总结并更新 skill

这已经是自进化雏形了。

但问题也开始暴露。



# 为什么简单自动更新不够

视频里提到，单轮轨迹驱动的自动沉淀看起来很美，但真实落地会出问题。

## 1. 质量不稳定

模型提取出的 skill 不一定真的有价值。

有时只是一次没什么价值的对话，也可能生成无用 skill。


## 2. 更新后反而变差

已有 skill 本来还能用，自动更新之后反而效果下降。

也就是：

- 新版本不一定比旧版本强
- 自动更新本身可能引入回退


## 3. skill 库越来越臃肿

常见问题：

- 重复
- 过时
- 半成品
- 描述越来越长
- 难维护、难阅读


## 4. 企业级场景风险更大

个人 agent 的任务比较分散，进化偏一点，影响还有限。

企业级 agent 不一样。

企业场景通常是：

- 海量任务
- 高同质化任务
- 高频重复执行

例如客服 agent 每天都在处理：

- 退款查询
- 订单问题
- 投诉处理

虽然任务类型相似，但每个用户的话术、上下文、表达方式都不同。

如果还是按“单轮轨迹”去赌这次有没有总结价值，赌错几十次后，skill 体系就会被带偏。



# 不要走 Prompt 过拟合老路

视频里明确反对一种常见做法：

出了一个问题，就往 prompt 里再补一句约束。

再出一次问题，再补一句。

结果就是：

- prompt 从几十字膨胀到几千字
- 规则越来越多
- 系统越来越脆
- 可解释性和可维护性越来越差

这本质上就是过拟合。

skill 自进化不能靠无限加提示词解决。



# 离线人工优化也不是最终答案

有些团队会采用更稳的方式：

- 先离线收集一批轨迹
- 人工生成或更新 skill
- 再做审核
- 再做回归评测
- 通过后灰度上线

这个流程很稳。

但它不是严格意义上的“自进化”。

因为关键决策还在人手里：

- 要不要改
- 改成什么
- 什么时候上线

本质上仍然是“人工监督下的半自动优化”。



# 真正可落地的四种方式

视频里总结了 4 种更科学的 skill 自进化思路。



# 1. 执行反馈驱动

核心思想：

不是看对话轨迹像不像有价值，而是看真实执行结果是否证明这个 skill 有价值。

重点：

- 基于结果判断
- 不是基于猜测判断
- 只有稳定产生收益，才沉淀 skill

适合场景：

- 对结果可验证的任务
- 有明确成功/失败信号的任务
- 对正确率要求高的企业任务

优点：

- 精度更高
- 噪音更少
- 不容易把无价值经验写进 skill

实践理解：

先看“是否真提升了执行效果”，再决定：

- 存储 skill
- 更新 skill
- 删除 skill



# 2. 轨迹蒸馏

核心思想：

不要盯着一条轨迹看，而是看一批轨迹，从大量成功/失败案例里提炼稳定模式。

重点：

- 看群体样本
- 找高频模式
- 找可复用模式
- 再沉淀成 skill

视频中的典型例子：

如果一个编程 agent 跑了很多任务后发现，大量成功案例都遵循下面流程：

- 先需求分析
- 再画流程图
- 最后编码

那么这就是一个稳定模式。

此时就可以提炼成一个通用 skill，例如：

- 项目规划
- 编码前分析流程

优点：

- 通用性更强
- 稳定性更高
- 不依赖单次偶然表现



# 3. 压缩与增强

这个方式主要解决“skill 库越进化越肥”。

它分两步。

## 压缩

定期对 skill 库做：

- 去重
- 合并
- 抽象

例如：

如果 skill 库里有很多“写邮件”的变体：

- 写学术邮件
- 写营销邮件
- 写跟进邮件
- 写通知邮件

而它们核心逻辑其实非常接近，就可以先压缩成一个通用的“写邮件” skill。


## 增强

压缩之后，再从通用能力往外扩展细分能力。

例如：

- 学术邮件版
- 营销邮件版
- 客诉回复版

这样做的结果是：

- skill 库更瘦
- skill 覆盖面更广
- 结构更清晰



# 4. 强化学习驱动

这是四种方式里最重的一种，但长期价值最高。

核心思想：

不用单轮轨迹评价 skill，而是用长期任务结果和奖励信号评价。

也就是：

- 每次任务结束后打分
- 积累大量交互结果
- 从高分行为中学习稳定策略
- 再把策略固化进 skill

视频中的客服例子很典型：

如果系统发现，在用户情绪强烈不满时，先说：

“抱歉，我先帮你确认一下”

这一类表达，长期看满意度更高。

那么这个策略就值得被写进 skill。

优点：

- 看长期收益
- 更贴近真实业务目标
- 学到的是经过实战验证的策略

缺点：

- 慢
- 重
- 对反馈体系要求高



# 四种方式怎么选

视频结论不是“只有一种正确答案”，而是可以混用。

可以这样理解：

- 执行反馈驱动：先保证沉淀的 skill 真有用
- 轨迹蒸馏：从大量案例中抽稳定模式
- 压缩与增强：控制 skill 库规模和结构
- 强化学习驱动：让系统追求长期最优

更现实的企业方案通常是组合拳。



# 企业级推荐落地路线

如果是企业级 agent，比较稳的路线可以是：

## 第一阶段：先别追求完全自动

先做：

- skill 版本管理
- skill 效果评估
- skill 上下线机制
- 回滚机制

先把“能控”做好。


## 第二阶段：引入执行反馈驱动

先让系统学会基于结果判断：

- 哪些经验该保留
- 哪些经验该丢弃

不要一开始就让模型自由改库。


## 第三阶段：做批量轨迹蒸馏

从高频场景中提炼标准流程。

适合优先做的场景：

- 客服
- 销售跟进
- 报表生成
- 编码规范执行
- 审核类任务


## 第四阶段：定期压缩 skill 库

建立固定机制：

- 去重
- 合并
- 标准化
- 过期清理

不要等 skill 库烂掉再治理。


## 第五阶段：成熟后再引入强化学习

当你已经有：

- 稳定的业务指标
- 任务评分机制
- 足够多的历史数据

再考虑用强化学习驱动长期优化。



# 设计自进化系统时要重点关注

## 1. skill 不是记忆垃圾桶

不是所有对话都值得沉淀。

要先判断：

- 是否高频
- 是否稳定
- 是否可复用
- 是否能提升结果


## 2. 更新必须可回滚

自动更新不是越快越好。

必须保留：

- 版本
- diff
- 评测结果
- 回退能力


## 3. 评价标准要绑定业务结果

不能只看“模型觉得这个总结不错”。

更应该看：

- 成功率
- 满意度
- 耗时
- 错误率
- 人工介入率


## 4. skill 库要长期治理

治理动作至少包括：

- 去重
- 合并
- 分类
- 下线无效 skill
- 拆分过大的 skill



# 我对这个视频的理解

这个视频真正想讲的，不是“让 agent 自动写 skill”这么简单。

核心是：

从“生成 skill”升级到“治理 skill”。

也就是从一次性建设，变成持续演化。

真正难的不是：

- 怎么生成一个 skill

而是：

- 怎么判断它值不值得存在
- 怎么证明它比旧版本更好
- 怎么避免 skill 库越来越乱
- 怎么让进化方向贴近真实业务收益

所以企业级自进化设计，本质上是一个：

- 经验沉淀系统
- 质量控制系统
- 长期优化系统



# 一句话总结

skill 自进化不是“自动把每次对话写进知识库”，而是“基于结果、批量经验、结构治理和长期奖励，持续把有效经验沉淀成可复用能力”。
