# 工作原理与触发机制

> 来源：[Skills 工作原理](https://www.runoob.com/skills/how-skills-work.html) / [Skills 触发机制](https://www.runoob.com/skills/skills-trigger.html)

## 一、渐进式披露（Progressive Disclosure）

智能体靠**读文件**知道某个 Skill 能做什么。Skills 采用渐进式披露方式，在不同阶段加载不同详细程度的信息，使代理可以管理大量技能而不耗尽上下文空间。

### 三个阶段

| 阶段 | 加载内容 | 典型大小 |
|---|---|---|
| 1. 发现阶段 Discovery | name + description | 约 100 tokens |
| 2. 激活阶段 Activation | 完整 SKILL.md | 建议不超过 5000 tokens |
| 3. 执行阶段 Execution | 脚本、参考资料等 | 按需加载 |

1. **发现**：对话开始时扫描所有技能文件夹，只读 name 和 description，足以判断相关性
2. **激活**：判断描述与用户请求匹配后，将完整 SKILL.md 加载到上下文
3. **执行**：按指令执行任务，可能调用脚本、读取参考资料或其他资源

> 关键：**SKILL.md 正文不参与触发判断**，只有决定使用后才读取正文。

## 二、触发判断机制

- Skills 不是被用户"调用"的，而是由 Claude 自主决定"是否使用"
- 启动时所有 Skill 的 name + description 进入上下文
- 用户发消息后，Claude 判断"这个任务复杂到需要参考专门指令吗？"

### 什么样的任务会触发

| 请求类型 | 示例 | 是否触发 | 原因 |
|---|---|---|---|
| 简单单步任务 | "读取这个 PDF" | 通常不触发 | 直接处理更高效 |
| 复杂多步任务 | "提取 PDF 表格并转 Excel" | 触发 | 需要专门工作流 |
| 专业领域操作 | "合并三个 PDF 并加水印" | 触发 | 涉及特定工具链 |
| 输出有格式要求 | "生成符合公司模板的 Word 报告" | 触发 | 需要特定格式规范 |

> Skill 很少被触发，通常是任务描述过于简单或 description 不够精准。测试时应使用**复杂、具体的用户请求**。

## 三、Description 触发策略

description 是触发的**唯一凭据**：

1. **列举具体场景**：不只写"做什么"，还要写"什么时候用"
   ```yaml
   description: >
     处理 Excel 和 CSV 文件，包括：读取数据、清洗格式、生成图表、
     计算统计指标、合并多个表格。当用户提到 Excel、xlsx、CSV、
     表格数据、数据清洗、财务报表时，应优先使用此 Skill。
   ```
2. **使用"推动性"语言**：Skills 系统天然倾向"少触发"，加入推动性语句提升触发率
   ```yaml
   description: >
     生成专业的 PowerPoint 演示文稿。当用户需要制作幻灯片、PPT、演讲稿、
     汇报材料时，必须使用此 Skill，即使用户没有明确说"用 pptx 格式"。
   ```
3. **列出关键词**：在描述末尾附上触发关键词列表

## 四、触发冲突处理

多个 Skill 同时匹配时，Claude 按匹配程度选最相关的一个。避免冲突需保持 description 边界清晰：

| 冲突场景 | 解决方案 |
|---|---|
| 两个 Skill 都处理 PDF | 区分具体操作："PDF 创建" vs "PDF 读取" |
| 通用与专用 Skill 重叠 | 专用 Skill 明确写出区别于通用 Skill 的场景 |
| 功能相似的两个 Skill | 考虑合并为一个，内部分支处理 |

> 原则：description 应当**"排他性"地描述适用场景**。能做什么 ≠ 应该什么时候用。

skill-creator 提供 description 优化脚本（详见 [04.描述编写与触发优化](../03.编写Skill/04.描述编写与触发优化.md)）：

