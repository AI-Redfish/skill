# Skill 定义与管理方法论

> 本文是设计思想层面的系统化方法论，与教程实操笔记互补：触发/描述写法见 [描述编写与触发优化](../03.编写Skill/04.描述编写与触发优化.md)，脚本/依赖/测试等工程化细节见 [04.工程化](../../README.md#04工程化--生产级质量)，本文的"海量 Skill 分层加载"与 [工作原理与触发机制](../01.基础概念/02.工作原理与触发机制.md) 的渐进式披露相呼应。

## 一、总览

这个文档用于整理“如何定义、编写、使用和规模化管理 Skill”。

Skill 不是普通提示词的堆砌，而是把一类**高频、可复用、边界清晰**的任务，封装成 AI 能识别、能调用、能稳定复现的操作说明。

一句话理解：

> Skill = 面向特定任务的标准作业说明书。

一个完整的 Skill 设计，需要回答四个问题：

- **做什么**：Skill 的任务边界是什么
- **什么时候做**：什么场景下应该触发
- **怎么做**：触发后按什么流程执行
- **做到什么程度算完成**：最终交付物和验收标准是什么

目录主线可以概括为：

```text
先澄清任务
  ↓
判断是否适合封装成 Skill
  ↓
定义 Skill 的边界、触发条件、输入和输出
  ↓
把执行流程写成可复用的操作手册
  ↓
当 Skill 数量变多时，用上下文工程管理加载成本、注意力和任务状态
```

## 二、基础认知

### 1. 什么是 Skill

Skill 本质上是一份可被 AI 自动识别并调用的能力说明。它需要把下面几件事说清楚：

- 解决什么问题
- 在什么情况下使用
- 触发后按什么步骤执行
- 最终交付什么结果
- 依赖哪些工具、资料或上下文
- 哪些场景不应该使用

好的 Skill 不是“让 AI 更努力”，而是把成熟工作流写成 AI 可以稳定执行的规则。

### 2. Skill 和 Prompt 的区别

普通 Prompt 更像一次性的指令，适合临时任务。

Skill 更像可复用的流程资产，适合反复出现、结构稳定、边界明确的任务。

区别可以这样理解：

| 类型 | 重点 | 适用场景 |
| --- | --- | --- |
| Prompt | 一次性表达需求 | 临时问答、简单任务 |
| Skill | 固化一套执行流程 | 高频任务、复杂任务、团队复用 |

Skill 的价值不是“写一段更长的提示词”，而是让 AI 在同类任务中持续复用同一套判断标准和执行流程。

### 3. 适合封装成 Skill 的任务

优先封装成 Skill 的任务通常具备这些特征：

- 高频重复出现
- 流程相对固定
- 输出结构比较稳定
- 对执行顺序有要求
- 普通提示词容易遗漏关键步骤
- 需要明确的质量标准或验收标准

典型例子：

- 需求整理 / 输出 PRD
- 页面方案设计
- 代码评审
- 测试用例生成
- MCP Server 创建
- 特定平台操作说明
- 文档结构化整理
- 视频或文章笔记整理

不适合优先封装成 Skill 的任务：

- 一次性、低频、不可复用的任务
- 目标极其模糊的探索性任务
- 边界很大、同时覆盖多个角色的大杂烩任务
- 每次输入差异巨大，难以沉淀稳定流程的任务

## 三、Skill 设计原则

### 1. 任务边界清晰

一个 Skill 最好只解决一类问题，不要把多个不同能力揉在一起。

例如：

- 好：`PRD 生成`、`前端页面设计`、`MCP Server 创建`
- 不好：`产品设计 + 前端开发 + 测试 + 部署一体化大杂烩`

原则：**一个 Skill 只做一件事，但把这一件事做完整。**

### 2. 触发条件明确

AI 是否能正确调用 Skill，很大程度取决于描述是否能让模型快速判断“该不该用”。

因此要写清：

- 用户会怎么表达这个需求
- 哪些关键词出现时适合触发
- 哪些场景不适合触发
- 与相似 Skill 的区别是什么

例如：

- 当用户说“帮我输出 PRD”“梳理需求”“补产品方案”时，适合触发 PRD 类 Skill
- 当用户明确要求“直接改代码”时，不应优先触发 PRD 类 Skill

原则：**触发条件越像真实用户语言，Skill 越容易被正确命中。**

### 3. 输入要求明确

写清楚 Skill 执行前依赖哪些信息。

常见输入包括：

- 用户目标
- 目标平台
- 现有资料
- 文件路径
- 技术栈
- 输出格式要求
- 约束条件

如果输入不完整，也要写明处理方式：

- 先询问缺失信息
- 不要在关键假设不明时直接开工
- 可以继续时，显式标注假设项

很多 Skill 失败，不是执行差，而是带着错误假设开始执行。

### 4. 执行步骤有顺序

Skill 应该告诉 AI：拿到任务后先做什么，再做什么，最后产出什么。

一个常见流程是：

1. 理解目标
2. 检查输入是否充分
3. 缺信息时先追问
4. 按既定流程执行
5. 输出结构化结果
6. 必要时给出下一步建议

原则：**Skill 不是散文说明，而是一套可执行流程。**

### 5. 输出结果可验证

好的 Skill 不是“帮用户做一下”，而是要明确交付物。

例如：

- 输出一份结构化 PRD
- 产出页面线框和交互说明
- 生成一个可运行的 MCP Server 骨架
- 给出明确的实施步骤和检查清单

原则：**完成标准越具体，结果越稳定。**

### 6. 排除项写清楚

除了说明“该做什么”，还要说明“不要做什么”。

例如：

- 不要在需求不清时直接编码
- 不要脱离给定技术栈随意替换方案
- 不要输出与目标无关的大段扩展内容
- 不要把多个角色的工作一次性混合输出

原则：**排除项越清楚，Skill 越稳。**

## 四、Skill 标准结构

### 1. 名称 Name

名称要短、准、可识别。

建议：

- 直接体现用途
- 避免空泛命名
- 尽量让人一眼看出“用来干嘛”

例如：

- `skill-creator`
- `frontend-design`
- `mcp-builder`
- `prd-writer`

不建议：

- `helper-pro`
- `smart-agent`
- `my-awesome-skill`

原则：**名字优先表达功能，不优先表达酷炫。**

### 2. 描述 Description

描述是最关键的部分之一，因为模型通常会靠它判断是否启用该 Skill。

好的描述应该同时包含：

- 适用任务
- 典型输入
- 产出结果
- 使用边界

推荐公式：

```md
用于处理【任务类型】。
当用户提出【典型表达】时使用。
它会完成【关键步骤】，并输出【最终产物】。
不适用于【排除场景】。
```

示例：

```md
用于把零散需求整理成结构化 PRD。
当用户要求梳理需求、输出 PRD、补齐产品方案时使用。
它会先识别缺失信息，再组织功能目标、用户流程、页面需求、验收标准。
不适用于直接编码实现类任务。
```

原则：**Description 要同时服务触发判断和执行预期。**

### 3. 使用场景 When to use

建议显式列出：

- 适用场景
- 不适用场景
- 与相似 Skill 的区别

这样能提高触发准确率，降低误调用概率。

### 4. 输入 Inputs

输入要求要明确写出：

- 执行前需要用户提供什么
- 哪些信息可以从上下文自动读取
- 哪些信息缺失时必须追问
- 哪些信息可以合理假设

原则：**不要让 Skill 在关键前提不明时强行执行。**

### 5. 执行步骤 Process

执行步骤是 Skill 的主体。

好的步骤要满足：

- 顺序清楚
- 每步动作明确
- 不写空话
- 能直接指导模型执行

示例：

```md
1. 识别用户目标和约束
2. 判断信息是否完整
3. 若缺信息，先提出关键问题
4. 按模板组织内容
5. 输出结果并补充后续建议
```

原则：**每一步都应该是一个明确动作，而不是泛泛要求。**

### 6. 输出格式 Output

输出格式越稳定，Skill 的复用性越高。

可以规定：

- 使用 Markdown
- 固定章节结构
- 使用表格、清单或编号列表
- 结尾附待确认项

例如 PRD 类 Skill 可以固定包含：

- 背景
- 目标
- 功能列表
- 用户流程
- 非功能要求
- 验收标准
- 风险与待确认项

### 7. 示例 Examples

高质量 Skill 往往会给出示例，以帮助模型理解：

- 什么请求会触发
- 应该如何响应
- 结果大致长什么样

示例最好贴近真实用户说法。

例如：

- “帮我把这个想法整理成 PRD”
- “根据这个需求做一个后台页面方案”
- “帮我创建一个用于天气查询的 MCP Server”

原则：**示例越贴近真实对话，触发效果通常越好。**

## 五、执行流程与常用 Prompt

### 1. 执行前先澄清任务

复杂任务不能直接做，必须先补全信息。

建议把“先提问再执行”写进 Skill：

- 如果关键信息缺失，先提问
- 不要擅自补关键业务前提
- 只有在信息充分时再进入执行
- 如果可以基于合理假设继续，要显式写出假设

### 2. 常用任务澄清 Prompt

适用于让 AI 先理解需求，再判断是否需要补充信息。

```md
帮我 XXX。

你看对于这个功能你还有什么不明白的，有的话你提出来。
如果没有的话，你先给我列一下，实现这个功能，前后端的一个任务列表。
没问题的话再介入开发。
```

这个 Prompt 的核心价值：

- 先让 AI 理解任务
- 让 AI 主动暴露不确定点
- 先产出任务拆解
- 用户确认后再进入开发

原则：**不要让 AI 带着错误假设直接开工。**

### 3. 推荐执行顺序

```text
理解用户目标
  ↓
检查输入是否完整
  ↓
缺信息时先追问
  ↓
信息充分后拆解任务
  ↓
按 Skill 流程执行
  ↓
输出结构化结果
  ↓
标记假设、风险和待确认项
```

## 六、规模化管理：海量 Skill 加载

当 Agent 拥有大量 Skill 时，不应该把所有 Skill 的完整说明、参数 schema、示例和文档一次性塞进上下文。

原因是：**token 不只是上下文容量，也是模型的注意力预算。**

全量加载会带来几个问题：

- 工具太多，模型选择工具的准确率下降
- 无关 Skill 干扰当前任务判断
- 指令之间可能互相冲突
- 上下文越长，推理成本和延迟越高
- 模型可能忽略真正关键的指令

因此，大规模 Skill 系统更适合使用**渐进式披露**和**按需加载**。

### 1. L1：元数据索引层

Agent 启动时，只加载每个 Skill 的最小信息：

- Skill 名称
- 一句话描述
- 简单适用场景

这一层的目标不是让模型立刻掌握所有 Skill 的细节，而是让模型先建立一张技能地图。

原则：**先让模型知道有什么，不要一开始就让模型知道所有细节。**

### 2. L2：意图理解与动态注入层

当模型或系统编排层判断当前任务需要某个 Skill 时，再动态注入这个 Skill 的完整说明。

通常包括：

- 完整使用说明
- 工具 schema
- 参数格式
- few-shot 示例
- 典型输入输出

这样可以保证模型在真正执行某个 Skill 时，注意力集中在当前任务所需的信息上。

原则：**需要哪个 Skill，就加载哪个 Skill 的详细说明。**

### 3. L3：深水执行层

当任务进入复杂执行阶段，例如：

- 工具报错
- 需要查长文档
- 需要理解大量背景资料
- 需要处理复杂边界条件

这时才触发 RAG、文档检索或更深层的资料加载。

原则：**庞大资料库不要常驻 prompt，只在真正需要时打开。**

### 4. 冷启动延迟处理

动态加载可能带来延迟，因此需要在架构中增加优化手段：

- 使用轻量级语义路由，先把用户意图分流到对应 Skill 簇
- 对高频 Skill 做预热
- 使用 prompt cache 或 KV cache 降低重复加载成本
- 把常用 Skill 的元数据长期保留在索引层

核心思路：**不要完全依赖大模型在超大工具列表里实时搜索，而是先用便宜、快速的路由机制缩小范围。**

### 5. Skill 切换后的状态保持

如果旧 Skill 被卸载，新 Skill 接手任务，容易出现任务状态丢失。

解决方式是引入**任务快照机制**。

任务快照不保存完整对话历史，而是保存能恢复任务现场的最小状态：

- 当前任务执行到哪一步
- 已经产出了什么结果
- 中间变量和关键文件是什么
- 下一步要做什么
- 当前约束和假设是什么

Skill 切换时，把这份快照注入上下文，新 Skill 就可以接着执行。

原则：**不保留所有过程，只保留能恢复任务的关键状态。**

### 6. 架构选型边界

渐进式加载不是所有场景都必须使用。

如果只有二三十个 Skill：

- 可以直接使用语义过滤
- 配合精简 prompt
- 不必引入复杂的三层架构

如果有上百个 Skill，尤其是企业级 Agent 系统：

- 需要分层加载
- 需要语义路由
- 需要缓存机制
- 需要任务快照
- 可以进一步配合多 Agent 或 Swarm 架构

原则：**小规模系统追求简单稳定，大规模系统才需要分层、路由、缓存和状态管理。**

## 七、常见失败原因

### 1. 技能范围过大

一个 Skill 试图同时做分析需求、设计页面、写代码、写测试、部署上线。

结果通常是：

- 触发不准
- 输出发散
- 难以复用

解决办法：**拆 Skill。**

### 2. 描述过于空泛

例如：

- “帮助用户完成开发任务”
- “一个很强大的助手”

这种描述几乎无法指导模型判断触发时机。

解决办法：改成具体任务、具体场景、具体输出。

### 3. 没有写输入前提

输入前提不清楚，会导致 AI 在信息不足时乱猜。

解决办法：明确写出缺信息先提问。

### 4. 没有规定输出结构

输出格式不稳定，会导致每次产出都不一样，难以复用。

解决办法：规定固定输出模板。

### 5. 没有边界说明

没有边界说明会导致 Skill 与其他 Skill 冲突，或者被误用于不合适的任务。

解决办法：加入“不适用场景”和“不要做什么”。

### 6. 过度设计

Skill 数量很少时，直接用清晰描述和语义过滤可能已经足够。

如果为了几十个 Skill 引入复杂的多层加载、缓存和状态管理，反而会增加维护成本。

解决办法：根据规模选择架构，不要为了架构而架构。

## 八、模板

### 1. 通用 Skill 模板

```md
# Skill 名称

## 作用
用于处理【具体任务】。

## 何时使用
当用户提出【典型表达 1】、【典型表达 2】、【典型表达 3】时使用。

## 不适用场景
- 【场景 1】
- 【场景 2】

## 输入
执行前需要确认：
- 【输入项 1】
- 【输入项 2】
- 【输入项 3】

若关键信息缺失，先向用户提问，不要直接假设。

## 执行步骤
1. 理解用户目标与约束
2. 检查输入是否完整
3. 若缺信息，先发起澄清
4. 按既定结构完成任务
5. 输出结果，并标记待确认项

## 输出格式
使用 Markdown，包含：
- 【模块 1】
- 【模块 2】
- 【模块 3】
- 【模块 4】

## 注意事项
- 不要【禁止项 1】
- 不要【禁止项 2】
- 若无法确认，显式写出假设
```

### 2. 任务澄清模板

```md
帮我 XXX。

你看对于这个功能你还有什么不明白的，有的话你提出来。
如果没有的话，你先给我列一下，实现这个功能，前后端的一个任务列表。
没问题的话再介入开发。
```

### 3. 海量 Skill 加载面试回答模板

```md
Agent 加载海量 Skill 时，不建议全量加载，因为 token 不只是上下文容量，更是模型注意力预算。工具过多会造成注意力稀释、工具选择准确率下降、成本上升和延迟变高。

我会采用渐进式披露架构：

第一层是元数据索引层，启动时只加载 Skill 名称和一句话描述，让模型知道系统有哪些能力。

第二层是意图理解与动态注入层，当模型或语义路由判断需要某个 Skill 时，再注入完整 schema、参数格式和 few-shot 示例。

第三层是深水执行层，遇到复杂报错、长文档或复杂边界条件时，再通过 RAG 动态检索相关资料。

针对动态加载的冷启动问题，可以用轻量级语义路由、工具簇预判、prompt cache 和 KV cache 预热降低延迟。

针对 Skill 切换导致状态丢失的问题，可以使用任务快照机制，把任务进度、中间结果、下一步计划和当前约束压缩成结构化状态，在切换 Skill 时注入上下文。

最后，这套方案是否必要取决于规模。如果只有几十个 Skill，语义过滤加精简 prompt 就够了；如果是上百个 Skill 的企业级 Agent 系统，渐进式加载会更合理。
```

## 九、实践检查清单

写完一个 Skill 后，可以用下面的问题检查质量：

- 这个 Skill 是否只解决一类问题
- 名称是否能直接看出用途
- Description 是否能帮助模型判断触发时机
- 是否写清了适用场景和不适用场景
- 是否写清了输入要求
- 信息不足时是否要求先追问
- 执行步骤是否有明确顺序
- 输出格式是否稳定
- 是否写了不要做什么
- 是否有贴近真实用户表达的示例
- 是否能被多人复用和持续维护

如果 Skill 数量变多，再继续检查：

- 是否只在启动时加载元数据
- 是否按需注入完整 Skill 内容
- 是否有语义路由或工具簇筛选
- 高频 Skill 是否有缓存或预热策略
- Skill 切换时是否有任务快照
- 长文档是否通过 RAG 按需检索

## 十、最终总结

写 Skill 时，最重要的不是提示词写得多华丽，而是把一套成熟工作流压缩成 AI 能稳定复现的操作手册。

一个好 Skill 的标准是：

- 容易被正确触发
- 任务边界清楚
- 执行过程稳定
- 输出结果可复用
- 失败场景可预期
- 能随着使用持续迭代

当 Skill 数量较少时，清晰定义和精简提示词就足够重要。

当 Skill 数量变多时，问题会从“怎么写 Skill”升级为“怎么管理 Skill 的加载、注意力和状态”。这时就需要渐进式披露、语义路由、动态注入、缓存、RAG 和任务快照。

最终可以把 Skill 理解为：

> 把一个成熟工作流，封装成 AI 能稳定识别、按需调用、持续复用的能力单元。
