# Skill 方法论

## 一、什么是 Skill

Skill 本质上是把一类**高频、可复用、边界清晰**的任务，封装成一份可被 AI 自动识别并调用的能力说明。

它不是普通提示词的简单堆砌，而是把下面几件事说清楚：

- 这个 Skill 解决什么问题
- 在什么情况下应该触发
- 触发后应该按什么步骤执行
- 最终应该交付什么结果
- 依赖哪些工具、资料或上下文

一句话理解：**Skill = 面向特定任务的标准作业说明书。**

---

## 二、好 Skill 的核心特征

### 1. 任务边界清晰

一个 Skill 最好只解决一类问题，不要把多个不同能力揉在一起。

例如：

- 好：`PRD 生成`、`前端页面设计`、`MCP Server 创建`
- 不好：`产品设计 + 前端开发 + 测试 + 部署一体化大杂烩`

原则：**一个 Skill 只做一件事，但把这一件事做完整。**

### 2. 触发条件明确

AI 是否能正确调用 Skill，很大程度取决于描述是否能让模型快速判断“该不该用”。

因此要写清：

- 用户会怎么表达这个需求
- 哪些关键词出现时适合触发
- 哪些场景不适合触发

例如：

- 当用户说“帮我输出 PRD”“梳理需求”“补产品方案”时触发
- 当任务需要直接改代码时，不应优先触发 PRD 类 Skill

原则：**触发条件越像真实用户语言，Skill 越容易被正确命中。**

### 3. 输出结果可验证

好的 Skill 不是“帮用户做一下”，而是要明确交付物。

例如：

- 输出一份结构化 PRD
- 产出页面线框和交互说明
- 生成一个可运行的 MCP Server 骨架
- 给出明确的实施步骤和检查清单

原则：**让 Skill 的完成标准具体、可检查、可复用。**

### 4. 步骤要有执行顺序

Skill 应该告诉 AI：拿到任务后先做什么，再做什么，最后产出什么。

一个常见的顺序是：

1. 理解目标
2. 检查输入是否充分
3. 缺信息时先追问
4. 按既定流程执行
5. 输出结构化结果
6. 必要时给出下一步建议

原则：**Skill 不是一段散文说明，而是一套可执行流程。**

## 三、Skill 撰写的推荐结构

虽然不同平台格式略有区别，但优质 Skill 通常都包含以下内容。

## 1. 名称（Name）

名称要短、准、可识别。

建议：

- 直接体现用途
- 避免空泛命名
- 尽量让人一眼看出“用来干嘛”

例如：

- `skill-creator`
- `frontend-design`
- `mcp-builder`
- `prd-writer`

不建议：

- `helper-pro`
- `smart-agent`
- `my-awesome-skill`

原则：**名字优先表达功能，不优先表达酷炫。**

## 2. 描述（Description）

描述是最关键的部分之一，因为模型通常会靠它判断是否启用该 Skill。

好的描述应该同时包含：

- 适用任务
- 典型输入
- 产出结果
- 使用边界

推荐公式：

```md
用于处理【任务类型】。
当用户提出【典型表达】时使用。
它会完成【关键步骤】，并输出【最终产物】。
不适用于【排除场景】。
```

示例：

```md
用于把零散需求整理成结构化 PRD。
当用户要求梳理需求、输出 PRD、补齐产品方案时使用。
它会先识别缺失信息，再组织功能目标、用户流程、页面需求、验收标准。
不适用于直接编码实现类任务。
```

原则：**Description 要同时服务“触发判断”和“执行预期”。**

## 3. 使用场景（When to use）

建议显式列出：

- 适用场景
- 不适用场景
- 与相似 Skill 的区别

这样做有两个好处：

- 提高触发准确率
- 降低误调用概率

## 4. 输入要求（Inputs）

写清楚这个 Skill 依赖什么信息。

例如：

- 用户目标
- 目标平台
- 现有资料
- 文件路径
- 技术栈
- 输出格式要求

如果输入不完整，也要写明：

- 先询问缺失信息
- 不要在关键假设不明时直接开工

这点很重要，因为很多 Skill 失败，不是执行差，而是**带着错误假设开始执行**。

## 5. 执行步骤（Process）

这是 Skill 的主体。建议使用编号步骤。

好的步骤要满足：

- 顺序清楚
- 每步动作明确
- 不写空话
- 能直接指导模型执行

例如：

```md
1. 识别用户目标和约束
2. 判断信息是否完整
3. 若缺信息，先提出关键问题
4. 按模板组织内容
5. 输出结果并补充后续建议
```

原则：**每一步都应该是一个明确动作，而不是泛泛要求。**

## 6. 输出格式（Output）

要明确规定结果长什么样。

可以规定：

- 使用 Markdown
- 固定章节结构
- 使用表格/清单/编号列表
- 结尾附“待确认项”

例如：

- 背景
- 目标
- 功能列表
- 用户流程
- 非功能要求
- 验收标准
- 风险与待确认项

原则：**输出格式越稳定，Skill 的复用性越高。**

## 7. 示例（Examples）

高质量 Skill 往往会给出示例，以帮助模型理解：

- 什么请求会触发
- 应该如何响应
- 结果大致长什么样

示例最好贴近真实用户说法，而不是只写抽象说明。

例如：

- “帮我把这个想法整理成 PRD”
- “根据这个需求做一个后台页面方案”
- “帮我创建一个用于天气查询的 MCP Server”

原则：**示例越贴近真实对话，触发效果通常越好。**

## 四、Skill 撰写技巧

## 1. 用“任务语言”写，不要只用“功能语言”写

用户通常不会说：

- “请调用一个需求分析 Skill”

用户更可能说：

- “帮我梳理这个需求”
- “给我出个 PRD”
- “把这个页面方案补完整”

所以 Skill 描述里要尽量使用真实用户表达。

原则：**站在用户提问方式上写触发词，而不是站在作者命名方式上写。**

## 2. 把“先提问再执行”写进规则

很多复杂任务不能直接做，必须先补全信息。

因此建议在 Skill 里明确加入：

- 如果关键信息缺失，先提问
- 不要擅自补关键业务前提
- 只有在信息充分时再进入执行

这比“硬生成结果”更稳定。

## 3. 把约束写成可执行规则

少写：

- “认真思考”
- “尽量完善”
- “输出高质量结果”

多写：

- “先列出缺失信息，再决定是否继续”
- “输出必须包含目标、流程、验收标准”
- “若无法确认，显式标注假设项”

原则：**抽象要求不如明确动作。**

## 4. 把大任务拆成阶段

复杂 Skill 最好拆成阶段，例如：

- 理解阶段
- 澄清阶段
- 执行阶段
- 交付阶段

这样既提升稳定性，也更符合真实工作流。

## 5. 把“不要做什么”写出来

除了说明“该做什么”，还要说明“不要做什么”。

例如：

- 不要在需求不清时直接编码
- 不要脱离给定技术栈随意替换方案
- 不要输出与目标无关的大段扩展内容
- 不要把多个角色的工作一次性混合输出

原则：**排除项越清楚，Skill 越稳。**

## 6. 适度模板化

很多成功 Skill 都有固定模板，这是优点，不是缺点。

因为模板化意味着：

- 结果更稳定
- 更容易复用
- 更便于后续二次加工

但模板不要过重，否则会让结果生硬。

最佳状态是：**框架固定，内容灵活。**

## 五、常见失败原因

## 1. 技能范围过大

一个 Skill 试图同时做：分析需求、设计页面、写代码、写测试、部署上线。

结果通常是：

- 触发不准
- 输出发散
- 难以复用

解决办法：**拆 Skill。**

## 2. 描述过于空泛

例如：

- “帮助用户完成开发任务”
- “一个很强大的助手”

这种描述几乎无法指导模型判断触发时机。

解决办法：改成具体任务、具体场景、具体输出。

## 3. 没有写输入前提

导致 AI 在信息不足时乱猜。

解决办法：明确写出缺信息先提问。

## 4. 没有规定输出结构

导致每次产出格式都不一样，难以复用。

解决办法：规定固定输出模板。

## 5. 没有边界说明

导致与其他 Skill 冲突，或者被误用于不合适的任务。

解决办法：加入“不适用场景”。

## 六、一个通用 Skill 模板

下面是一个通用写法，可以直接套用。

```md
# Skill 名称

## 作用
用于处理【具体任务】。

## 何时使用
当用户提出【典型表达 1】、【典型表达 2】、【典型表达 3】时使用。

## 不适用场景
- 【场景 1】
- 【场景 2】

## 输入
执行前需要确认：
- 【输入项 1】
- 【输入项 2】
- 【输入项 3】

若关键信息缺失，先向用户提问，不要直接假设。

## 执行步骤
1. 理解用户目标与约束
2. 检查输入是否完整
3. 若缺信息，先发起澄清
4. 按既定结构完成任务
5. 输出结果，并标记待确认项

## 输出格式
使用 Markdown，包含：
- 【模块 1】
- 【模块 2】
- 【模块 3】
- 【模块 4】

## 注意事项
- 不要【禁止项 1】
- 不要【禁止项 2】
- 若无法确认，显式写出假设
```

## 七、适合优先封装成 Skill 的任务

优先做成 Skill 的任务，一般有下面几个特点：

- 高频重复出现
- 流程相对固定
- 输出结构比较稳定
- 对执行顺序有要求
- 普通提示词容易遗漏关键步骤

典型例子：

- 需求整理 / 输出 PRD
- 页面方案设计
- 代码评审
- 测试用例生成
- MCP Server 创建
- 特定平台操作说明
- 文档结构化整理

---

## 八、我的总结

写 Skill 时，最重要的不是“提示词写得华丽”，而是把下面四件事写清楚：

- **做什么**：Skill 的任务边界
- **什么时候做**：触发条件和适用场景
- **怎么做**：执行步骤和规则
- **做到什么程度算完成**：输出结果和验收标准

可以把 Skill 理解为：

> 把一个成熟工作流，压缩成 AI 能稳定复现的操作手册。

因此，一个好 Skill 的标准不是“看起来高级”，而是：

- 容易被正确触发
- 过程稳定
- 结果可复用
- 边界清楚
- 能持续迭代
