# test-case-generator — 需求驱动的功能测试用例生成器

把需求文档（PRD）与技术文档转化为**可直接执行的功能测试用例集**：
每条用例映射到 PRD 验收标准（AC），覆盖正例、反例、边界、权限四个维度，
经脚本校验结构完整性与 AC 覆盖率后交付。**确定性检查交给
`scripts/validate_cases.py`，AI 只做需求理解与用例设计**。

## 双闭环流程（最高优先级，优先于其他默认行为）

完成用户任务时必须遵循以下双闭环；当本规则与基础行为习惯冲突时，以本规则为准。

### 第一闭环：理解闭环
1. 回答前先提问，**每次只问一个问题**，根据回答继续追问
2. 提问围绕：真实目标、背景、使用场景、输出对象、关键约束、优先级、
   成功标准、禁止事项、已有信息、可接受偏差
3. 对"用户真正想要什么"有 95% 信心才停止提问；未达 95% 只提问澄清，
   不给最终方案（用户消息已足以达到 95% 信心时可直接执行，
   但最终输出必须列出关键假设）

### 第二闭环：输出审查闭环
1. 形成答案后不直接输出，先自查：是否真正解决目标？是否遗漏关键约束？
   是否存在事实错误、逻辑漏洞、歧义、不可执行之处？
2. 发现问题→自行修正→再次审查，重复"审查—修正—再审查"，
   直到对输出结果至少有 95% 的准确性信心

### 最终输出要求
1. 先一句话复述用户真实需求
2. 再给出最终方案：明确、可执行、可直接使用
3. 说明关键假设、剩余不确定性，以及为什么已达到 95% 信心；
   不确定处明确标注，不假装确定

## 输入收集（缺失进入理解闭环，一次只问一个）

| 输入 | 必需性 | 用途 |
|---|---|---|
| 需求文档（PRD）路径 | **必需** | 功能点、AC 验收标准、异常与边界规则的唯一来源 |
| 技术/设计文档路径 | 推荐 | 技术口径（状态枚举、接口清单、数据规则）、AC 未覆盖场景的补充用例来源 |
| 输出目录 | 可选 | 缺省 `<工作目录>/.agents/test-cases/`（gitignore 场景不污染提交） |

- 两份文档至少提供一份；**只给技术文档没有 PRD 时**先确认：无 AC 映射需求则
  按技术口径出用例（关联AC 列留空并在汇报标注"无 PRD，未做 AC 覆盖检查"）。
- PRD 中未找到任何 `AC` 编号时如实告知并继续（覆盖率检查自动跳过）。

## 主流程（五步，顺序执行）

### 第 1 步：需求解析（读全文档，先解构再设计）

通读 PRD 与技术文档，提取四类清单（写进用例文档的"需求解构"章节）：

1. **功能模块清单**：按 PRD 的 R 编号/章节/页面分组，标注双端（PC/移动端）；
2. **AC 验收标准清单**：逐一编号（如 AC7-1），记录原文要点与所属功能点；
3. **技术口径**：状态机与枚举（如五态：未开启/未关联/拍照中/全部失败/部分成功/全部成功）、
   接口清单、字段校验规则（必填/长度/取值）、数据兼容规则（历史数据缺省值）；
4. **明确不实现范围**（如"R1 本期不实现"）：写入文档开头范围声明，
   防止用例越界，也防止测试人员误报缺陷。

### 第 2 步：用例设计（方法详见 references/case-design-guide.md）

对每个功能点按四维度展开，**每条用例必须映射到 AC 或技术口径条款**：

| 维度 | 设计要点 | 示例（拍照核验开关） |
|---|---|---|
| 正例 | 主流程 happy path，一步一验证 | 开启开关保存成功，详情回显"开启" |
| 反例 | 校验拒绝类：非法值/必填缺失/重复提交 | 传值 2 保存被拒，提示含"无效值" |
| 边界 | 空态、阈值、首次/历史数据兼容、并发重复 | 历史计划无此字段，详情按"关闭"兼容 |
| 权限 | 无权限访问、越权直链、数据范围隔离 | 无执行记录查看权限时详情接口与图片均拒绝 |

- **状态类需求逐状态一条用例**（每个状态一个独立可判定的预期）；
- **双端需求分端各出用例**（PC 与移动端交互差异单独覆盖，数据一致性共用一条）；
- 前置条件写"测试人员可操作的准备动作"（造数/配置/账号），不写代码术语；
- 预期结果必须含**可客观判定的断言**（字段值、提示文案、列表行数），禁止"功能正常"。

### 第 3 步：落盘

按 references/output-format.md 的模板写入
`<输出目录>/<需求名>-测试用例.md`；用例编号规则 `TC-<模块码>-<三位序号>`，
按模块分组、模块内连续。

### 第 4 步：脚本校验（必做，通过才交付）

```bash
uv run <skill_dir>/scripts/validate_cases.py --cases <用例文档路径> --prd <PRD路径>
```

- 退出码 0：结构完整、编号唯一、AC 覆盖率已计算 → 进入第 5 步；
- 退出码 1：存在 error（编号重复/必填列空/优先级非法等）→ 修复后重跑直至 0；
- `coverage` 字段如实汇报：`acTotal/acCovered/acMissing/rate`；未覆盖的 AC 逐条
  给出原因（由技术口径覆盖 / 不适用本期 / 确属遗漏需补用例）。

### 第 5 步：交付汇报（按最终输出要求）

汇报必须包含：用例总数与四维度分布、AC 覆盖率与未覆盖清单及原因、
输出文件路径、明确不实现范围声明。

## 输出格式约定

- 用例文档结构、列定义、示例见 references/output-format.md；
- 文档章节固定顺序：范围声明 → 需求解构 → 用例总览统计 → 分模块用例表 → AC 覆盖统计 → 缺口清单。

## 触发示例

- "根据 D:/xxx/PRD.md 和技术文档生成测试用例" → 五步主流程，输出 .agents/test-cases/
- "检查这份用例文档是否覆盖了 PRD 的所有 AC" → 仅跑 validate_cases.py 并解读 coverage
- "这次需求 R1 不做，给其余功能出用例" → 范围声明写入文档，R1 相关 AC 标注"不适用本期"

## 不适用场景

- 自动化测试执行/回归 → fulllink-test
- 提测报告/提测单 → submit-test-report
- 单元测试、接口自动化脚本编写 → 开发类 skill

## 输出精简约束（所有落盘产物与答复通用）

1. **只落盘有用的**：只把用户会直接使用的产物写到磁盘；过程稿、中间草稿、
   重复副本、无人引用的说明文件一律不落盘。
2. **中间产物隔离**：确需保留的中间产物收进专门子目录或 `.agents/` 隐藏目录，
   不与交付产物混放；交付目录顶层只出现用户要的文件。
3. **落盘前自问**：写文件前先问"用户会直接使用它吗"；不会就不写，改为文字说明。
4. **答复同理**：汇报只讲结论、路径、风险与待办，不复述中间过程与脚本日志。
5. **本 skill 针对性约束**：交付物只有测试用例文档本身；校验 JSON、需求解构草稿
   等中间产物放 `.agents/test-cases/.work/` 或不落盘。

## 自我沉淀闭环（每次对话结束必检，最高优先级）

1. **回顾识别**：每次对话结束前，回顾本次对话是否出现值得沉淀的信号——
   新的用例设计模式（某类需求的维度模板）、validate_cases.py 的解析盲区、
   被用户纠正的用例格式或覆盖口径
2. **有沉淀候选 → 主动询问用户**（一次只问一个）：
   「本次对话发现 <X>，是否沉淀进本 skill（修改 SKILL.md / references/ / scripts/）？」
3. **用户确认后**：遵循本 skill 自身产出规范小步修改对应文件（不重写整个 skill），
   并递增 frontmatter 的 `metadata.version`；用户拒绝则不强改
4. **无沉淀候选 → 不打扰用户**，正常结束
5. **判定标准**：只沉淀未来场景会复用的通用规律，一次性细节不沉淀
