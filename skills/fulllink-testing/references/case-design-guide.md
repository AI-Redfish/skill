# 用例设计方法（case-design-guide）

从需求到用例的转化方法。核心原则：**一条用例只验证一件事**，
预期结果必须可客观判定，每条用例必须可追溯到 AC 或技术口径条款。

## 1. 需求解构方法

### 1.1 功能点提取

从 PRD 按"用户可感知的行为单元"切分功能点，粒度标准：
一个功能点 = 一次独立的用户操作意图（如"开启拍照核验开关并保存"是一个功能点，
"保存计划"不是一个功能点——它跨多个字段）。

- 以 PRD 的 R 编号 / 章节号为骨架，逐节扫描"系统应/支持/显示/提示"类句子；
- 技术文档补充 PRD 未展开的口径：状态枚举、字段校验、数据兼容、接口行为；
- **明确不实现范围**单独记录（本期不做的内容不产生用例，但要在文档声明防误报）。

### 1.2 AC 映射

- PRD 验收标准表（如 `AC7-1`、`AC7-M1`）逐条登记：编号、原文要点、所属功能点；
- 一条 AC 可能拆多条用例（如 AC7-10 五态展示 → 每态一条）；一条用例也可关联
  多条 AC（如一条用例同时验证 Web 与移动端同数据）；
- 技术文档口径裁决（如"抓拍失败不回滚任务完成"）若无对应 AC，以
  `TD-<章节>` 编号登记（Technical Detail），同样纳入映射跟踪。

## 2. 四维度展开法

对每个功能点依次过四个维度，问四个问题：

| 维度 | 提问模板 | 常见遗漏 |
|---|---|---|
| 正例 | 主流程成功后，用户看到什么？ | 只验证保存成功，漏验证**回显**与**列表刷新** |
| 反例 | 什么输入/操作必须被拒绝？提示是什么？ | 漏"提示文案具体内容"的断言 |
| 边界 | 空值/零条/最大值/首次使用/历史数据/重复提交会怎样？ | 漏历史数据兼容与并发重复提交 |
| 权限 | 无权限用户直接访问会怎样？数据范围是否隔离？ | 漏"直链绕过页面入口"的越权路径 |

### 2.1 状态类需求的特殊规则

需求含状态机/枚举态（如"未开启/未关联摄像头/拍照中/全部失败/部分成功/全部成功"）时：

- **每个状态至少一条独立用例**，前置条件写"如何构造该状态"；
- 状态间的**不可逆/单向约束**单独出用例（如"写入即终态，重新打开不变化"）；
- 由推导产生的展示态（不落库、由其他数据推导）也要有用例验证推导正确性。

### 2.2 双端需求的拆分规则

- **数据一致类**（两端读同一数据）：一条用例覆盖，预期写"Web 与移动端展示一致"；
- **交互差异类**（滑动/按键/布局）：分端各出用例，编号用模块码区分（如 `TC-M-`）；
- 移动端补充维度：手势边界（首尾不循环）、返回保留状态、加载失败重试。

### 2.3 历史数据与兼容

凡需求含"缺省值/兼容/迁移"字样，必须有一条：
存量数据（无新字段/旧值）在 新增、编辑回显、列表展示 三个入口的行为用例。

## 3. 用例编号与组织

- 编号 `TC-<模块码>-<三位序号>`，模块码取功能点英文/拼音缩写（如 `TC-PV-` 拍照核验）；
- 按模块分节（`### 模块名`），模块内序号连续；
- 建议模块码在同文档内保持唯一，避免不同模块撞号。

## 4. 优先级判定

| 级别 | 判定标准 |
|---|---|
| P0 | 主流程正例、资损/数据破坏类反例、核心权限隔离 |
| P1 | 一般反例、常用边界、状态类展示 |
| P2 | 低频入口、极端边界、提示文案细节 |

## 5. 自检清单（设计完成后逐条过）

- [ ] 每条 AC 都有 ≥1 条用例关联（或给出不适用原因）；
- [ ] 每个功能点四维度至少各 1 条（正例必有的前提下允许按需说明省略维度）；
- [ ] 状态类需求逐状态覆盖；
- [ ] 双端需求按 2.2 拆分；
- [ ] 预期结果无"正常/正确"类模糊词；
- [ ] 前置条件可由测试人员独立准备；
- [ ] 不实现范围已声明且无用例越界。
