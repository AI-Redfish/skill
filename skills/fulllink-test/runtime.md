# 测试运行方式与服务准备

> 测试模式①确认方式，③登记准备计划，④在业务 E2E 前执行本文件。
> 业务仓库内容只读；测试/编排脚本仅 Python（uv）或 Node.js。

## 1. 明确本轮运行方式

- 每个目标环境都明确 `executionMode: local | existing`，用户已说明则直接记录；
  未说明则询问“本次要本地编译启动，还是测试现成已启动的服务？”，不根据 localhost、
  环境名或默认地址猜测。初始化可登记常用方式，本轮使用方式须从用户指令或明确确认取得。
- `local`：本轮从用户指定分支的确定 commit 编译并启动被测项目。
  `existing`：使用台账记录的现成运行服务，不替用户构建、部署或重启。
- 本地业务服务可以连接已启动的中间件，但必须逐项标明实际地址及
  `provision: start | reuse`（本轮启动/复用现成服务），核实可用，避免混用环境。
  复用现成的其他业务服务也要登记来源与覆盖限制。
- 记录到 workspace.yaml `environments[].executionMode`、docs/04-env-matrix.md，
  以及本轮 plan.md。实际地址同步 env.json 对应环境；凭据仅 env.secret.json。

## 2. 从实际链路建立服务清单

读架构、模块链路、构建配置及启动配置，确定本轮链路必须具备的组件：
后端服务（网关、认证、业务服务、消费者等）、前端应用、Nginx、RabbitMQ、数据库、
Redis、注册/配置中心及其他第三方组件。不限于改动仓库；依赖服务也必须就绪。
只列实际需要的组件，不为所有项目无条件安装 Nginx 或 RabbitMQ。

清单逐项记录：来源仓库/应用、依赖关系、start/reuse、构建与启动命令、工作目录、
外置配置来源、地址/端口、就绪检查、超时、日志路径、停止方式。
信息不足先只读考古，仍缺必需配置、凭据或安装来源时明确阻断项，不能凭空补地址。

## 3. 本地模式：编译、启动与就绪检查（必执行）

1. **隔离构建**：将准备阶段确定的 commit 导出至
   `runs/<主题>/tmp/runtime/src/<仓库>/` 的非 Git 副本（例如 git archive；
   submodule/LFS 按实际项目要求导出并记录版本）。不使用带 .git 的 clone 作为构建目录，
   不复制用户未提交修改、旧构建产物或凭据。确保编译的是本轮指定 commit。
2. **工具与构建**：核实实际需要的 JDK/Maven、Node/pnpm、Docker 等版本；按项目构建
   文档安装依赖、编译后端，并构建或启动所需前端。原生构建/服务管理命令允许直接
   执行（不受测试脚本语言限制）；不运行仓库自带测试套件，按项目支持的参数跳过。
   锁文件保持原样，前端依赖安装使用对应锁文件的冻结安装方式。
   依赖、产物、缓存及外置测试配置放非 Git 副本/工作空间侧；不改业务源码修构建。
   构建失败记录命令、退出码与日志，相关链路 BLOCKED，不用旧产物冒充本次构建。
3. **准备依赖**：先检查 start/reuse 清单。缺失的本地组件按已登记安装方式与配置
   准备并启动，可使用项目已有容器镜像或本地安装；使用隔离的容器名、目录和端口。
   不覆盖已有实例或共享数据。端口冲突先识别进程，调整本轮外置配置/台账，不杀未知进程。
   需要的安装方式、资源或权限不可用则记 BLOCKED，说明恢复步骤。
4. **按依赖顺序启动**：基础中间件/注册配置中心 → 后端服务/消费者 → 前端与反向代理
   （实际顺序由依赖图决定）。Nginx 配置置于工作空间，先检查配置有效再启动；
   路由指向本轮的实际后端/前端。启动进程须能跨工具调用存活，记录 PID 或容器 ID、
   监听端口及日志；长期使用的编排脚本沉淀到仓库外 assets/probes/。
5. **确认正常才能跑相关 E2E**：就绪检查按明确间隔轮询到超时，同时检查进程退出、
   启动日志与实际协议响应。端口开放不等于服务正常：
   - 后端：健康接口及必要的注册、DB/MQ 连接状态；消费者链路检查实际消费者已连接。
   - Nginx：配置检查通过，实际入口可访问、路由到预期后端/前端，无启动错误。
   - RabbitMQ：AMQP 连接与认证、目标 vhost 可访问，业务所需 exchange/queue/binding
     与消费者就绪；不只查看管理页或进程。必要资源按项目正常初始化流程准备。
   - DB/Redis/其他依赖：验证实际账号和目标库/协议所需操作可用。
   检查脚本仅 Python（uv）或 Node.js，MCP 可辅助取证。记录证据与时间，
   这些是运行准备证据，不能代替业务 E2E 的 PASS。
6. 缺服务、编译失败、启动失败或就绪超时：阻断依赖该组件的测试，记录失败阶段、日志
   与未覆盖链路；不宣称全链路通过。互不依赖且已就绪的链路可继续。

## 4. 现成服务模式

明确入口、后端/中间件地址及由谁维护。使用台账服务，不编译、不部署、不重启共享服务。
在业务冒烟中核对所需服务实际可用；连接失败按环境阻断归因，不归为业务断言失败。
不新增强制部署指纹门禁；版本来源未知在报告明确标注，不能声称已验证指定 commit 部署。

## 5. 留证与收尾

- plan/report 记录运行方式、构建 commit/产物、服务 start/reuse、地址、就绪结果、
  PID/容器 ID 与日志路径。即使本地准备失败，也生成 Markdown、HTML 报告并尝试打开。
- 执行完清理本轮测试数据，停止本轮启动的进程/容器（依赖顺序反向）；若用户要求保留
  则列出仍在运行的服务与停止方法。复用的已有服务保持原状态，不停止、删除或重置。
- 原仓库和 repos/ 检出的执行前后只读检查继续执行，构建产物仅留在非 Git 副本。
