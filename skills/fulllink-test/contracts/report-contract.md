# 报告契约与对账断言标准

> 测试模式第③⑤步引用本文件。plan.md 与 report.md 必须严格按以下模板生成；
> 断言必须达到本文件标准，低于标准的只能记为 L0 诊断证据。

## 〇、报告产出约定（markdown + HTML）

每轮按 [run-records.md](../run-records.md) 创建唯一 run-id，在 `runs/<run-id>/`
落 report.md（本契约模板）；执行前登记 run.json，完成/阻断后同步结果并重建索引。
模块、主题、起止时间、环境和范围在元数据与报告中一致；随后**必须**执行：

```bash
python3 <skill_dir>/scripts/report_html.py <report.md>
```

同目录生成同名自包含 HTML（内嵌样式、PASS/FAIL 状态标色、无外部依赖）并自动用
系统浏览器打开供人查看；CI/无界面场景加 `--no-open`。report-assert.md（探针
断言表）可同法转换。

## 测试方式、数据与 UI 覆盖约定

每个测试点使用稳定编号（如 T001），从计划到执行明细、结果、数据和录像都用同一编号。
同一测试点在不同环境、不同尝试分别记明细，不用一次成功覆盖失败尝试。

- **测试方式**说明用户能理解的实际操作：UI 自动化、非 UI 脚本测试（API/消息/DB 等）、
  MCP 检查或人工测试；一个测试点有 UI 操作和 DB 脚本对账时写“UI 自动化 + 非 UI 脚本对账”。
  UI 自动化本身也是脚本，但不能只写“脚本”而隐藏是否操作过页面。
- **测试类型**（E2E/集成/单点）说明覆盖深度，**通道**（脚本/MCP/人工）说明执行工具来源；
  这两个字段不能代替测试方式。同一测试点多方式辅助时分别写工具和证据，不声称没执行的方式。
- **UI 适用性在计划阶段判断**：页面表单、按钮、权限展示、交互、跳转、页面结果或完整
  用户流程应优先 UI；纯后台任务/协议/无页面功能可不适用，但写明具体依据。
  后端改动影响页面用户流程时也要评估 UI，不能仅因“后端修改”判为不适用。
  无法判断时标“待确认”，不能为了省事或 UI 受阻而事后改判“不适用”。
- **预定 UI 未执行必须解释**：写具体原因、诊断证据、用户限定范围（若有）、
  实际替代方式、已验证内容、UI 未覆盖环节和恢复条件。例如登录失败、账号权限不足、
  页面入口不可用、浏览器/录制依赖异常；仅写“脚本已验证”“无需 UI”“时间不足”不充分。
  已尝试 UI 但中途失败需写最后完成步骤及未完成步骤，不能记成“UI 未尝试”。
- **结果分开表达**：预定 UI 被接口脚本替代时，接口断言可 PASS，UI 场景仍是
  BLOCKED/MANUAL/SKIPPED-降级；不得用接口 PASS 覆盖整条 UI/E2E 结论。
  UI 已执行但录屏缺失另记“录屏证据缺失”；录像待人工核对也不能写“UI 全部验证完成”。

每个测试点（包括 PASS）记录本次实际数据：来源环境、查询时间、选样 SQL/策略引用、
选中的业务标识与前置状态、页面输入/API 参数/消息体、预期结果及计算依据、实际结果、
差异、关联 ID 和清理状态。只记录判断所需字段；大数据/多条样本用本轮证据文件相对
链接，报告保留关键摘要，不能只链接脚本让读者猜数据。记录的是本轮快照，脚本和
fixtures 仍运行时选样，不把本轮 ID 固化到下一轮。凭据、token、Cookie 禁止入报告；
个人敏感信息脱敏，长整型标识用字符串。未执行项写“未取样/未执行”及原因，不填虚构数据。

执行时即按点/环境/尝试保存脱敏数据与步骤到
`evidence/<环境>/<模块>/<测试点编号>/attempt-<序号>/`，避免测后重查 DB 冒充改前快照。

## 三、对账断言标准（判定 PASS 的最低门槛）

| 场景 | 必须断言到 | 不算通过的反例 |
|---|---|---|
| E2E 业务流程 | 从真实页面/API/消息/任务入口触发，关联同一业务标识，核对最终业务结果和必要副作用 | 只打开页面、只调用健康检查、仅靠 mock 或直接改 DB 后查到记录 |
| 延迟/异步链路 | 触发后**轮询断言**：明确等待窗口与轮询间隔（如每 5s 查一次、最长 3min），到窗仍未生效才判 FAIL | "过了一会儿好像生效了" |
| 消息链路 | 发出的 messageId 在出口消息/落地记录中对上；routeKey、属性 key、值逐字段一致 | "队列收到消息了" |
| DB 副作用 | 改前查、改后查，精确到值与行数；条件更新场景断言不重复翻转 | "接口返回 200" |
| 扇出/广播 | 应到 N 条、实到 N 条，逐接收方核对 | "大部分都收到了" |
| 缓存 | 键存在性 + 值 + TTL；失效场景断言下一条消息即用新值 | "缓存里有东西" |
| SQL 改写 | EXPLAIN 走索引/兼容 ONLY_FULL_GROUP_BY 实测执行 | "SQL 语法没问题" |
| 性能 | 速率、错误数、资源上限推导（如 unacked ≤ 消费者数 × prefetch） | "感觉变快了" |

通用规则：

1. **L0 证据**（仅 HTTP 200、返回非空、页面可访问）只能记为诊断证据，不得标 PASS
2. **测试输入样本与预期值都在执行时从目标环境 DB 现查**（挖掘 SQL 见 05-test-data.md），
   禁止硬编码 ID/SN/样本值（业务数据是变化的）
3. 超过 JS 安全整数的 ID 一律按字符串处理（lib.js 已内置）
4. MQTT retained 消息：订阅会先收旧保留消息，断言必须带时间窗/去重
5. 证据要可复查：记录 messageId、查询 SQL、前后值快照，而不是"已验证"三个字
6. UI 自动化须全程录屏且节奏可人工查看；自动断言与人工视频核对分别记录，
   人工核对未完成不得将整轮 UI 验证总结为全部完成
7. 每个测试点都记录实际方式、所用数据、预期及实测；预定 UI 未完成项逐项说明原因、
   替代检查和缺口。报告以真实执行证据为准，不靠脚本存在或计划内容声称已测试
