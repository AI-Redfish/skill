# 报告契约与对账断言标准

> 测试模式第③⑤步引用本文件。plan.md 与 report.md 必须严格按以下模板生成；
> 断言必须达到本文件标准，低于标准的只能记为 L0 诊断证据。

## 〇、报告产出约定（markdown + HTML）

每轮测试在 `runs/<主题>/` 落 report.md（本契约模板）；随后**必须**执行：

```bash
python3 <skill_dir>/scripts/report_html.py <report.md>
```

同目录生成同名自包含 HTML（内嵌样式、PASS/FAIL 状态标色、无外部依赖）并自动用
系统浏览器打开供人查看；CI/无界面场景加 `--no-open`。report-assert.md（探针
断言表）可同法转换。

## 1. 变更清单（按 仓库×应用 分组；binary 组件单列"版本变更"节；无变更仓库列一行"无变更"）
| 仓库/应用 | 提交 | 主题 | 变更文件数 | 模块分组 |
|---|---|---|---|---|

## 2. 影响矩阵
| 链路 | 测试点 | 预期行为 | 测试类型 | 验证通道 | 资产/方式 | E2E 降级原因/缺口 |
|---|---|---|---|---|---|---|
（测试类型：E2E / 集成 / 单点；优先 E2E。验证通道：脚本〔沉淀库/本轮生成〕/ MCP / 人工）

## 3. 执行顺序
运行准备（local：编译→依赖→服务启动→就绪；existing：使用明确入口）
→ 冒烟 → 功能链路（列出顺序）→ 数据对账 → 压测（可选）

## 4. 关键假设
- <假设一条一行，如：existing 模式部署版本由用户提供，尚未独立核验>

## 5. 运行准备计划（逐环境）
| 组件/仓库/应用 | start/reuse 与来源 | 依赖 | 构建/启动/工作目录/配置 | 地址 | 就绪检查/超时 | 日志/停止方式 |
|---|---|---|---|---|---|---|
（明确 local/existing。local 从指定 commit 的仓库外非 Git 副本构建启动；

## 二、report.md 模板（`runs/<主题>/report.md`）

```markdown
# <主题> 测试报告

> 分支/commit：<...> | 环境：<env>（信息来源：工作空间环境台账 docs/04-env-matrix.md）
> 执行时间：<...> | 运行方式：<local/existing> | 结论：<通过 / 自动断言通过，UI 录像待人工核对 / 有阻断项 / 环境不符停止 / 部分未验证>

## 1. 结果矩阵
| # | 测试点 | 测试类型 | 通道 | 结果 | 证据摘要 |
|---|---|---|---|---|---|
（E2E 证据包含真实入口、链路、最终业务结果及关联标识；单点 PASS 不代表 E2E 通过）
（结果取值：PASS / FAIL / BLOCKED / MANUAL / SKIPPED-降级；证据必须可复查）

## 2. 逐条证据
（每个非 PASS 项与抽样 PASS 项：输入、预期、实测、差异、归因：
环境问题 / 部署版本问题 / 真实缺陷，附 messageId、SQL 前后值、耗时等）

## 3. 人工验证清单
| # | 验证点 | 操作步骤 | 对应提交 |
|---|---|---|---|
（脚本覆盖不了的点必须在此列出，禁止静默省略）

## 4. 降级与未验证项
| 项 | 原因（E2E 受阻/工具缺失/凭据未配置/环境不通） | 已验证范围 | 未覆盖环节与风险 |
|---|---|---|---|

## 5. 资产沉淀记录
（tmp/ → assets/probes/ 的迁移清单；docs 回填清单；新的挖掘 SQL 回填 05-test-data.md）
## 6. 测试数据清理清单（写操作类验证，无则省略）
| 项 | 环境标记 | 清理方式 | 状态 |
|---|---|---|---|
（仅清理本轮在目标测试环境产生的数据；不得修改业务仓库配置或文件）

## 7. Git 与黑盒组件只读检查
| 组件/登记名/实际 path | 被测分支/commit 或黑盒版本 | 执行前状态 | 执行后差异 | 检查结论 |
|---|---|---|---|---|
（空间内外组件目录始终只读，Git 指定分支只读解析 commit，不切 HEAD、不 fetch。
检查 Git 文件及元数据、未跟踪/忽略目录产物、黑盒交付物与配置；
列出意外写入并对话提示用户，不自动 reset/clean 或修复。）
环境中业务数据的变化另见逐条证据与清理清单。）

## 8. 构建、启动与服务就绪证据（逐环境）
| 组件 | start/reuse 与来源 | commit/构建产物/退出码 | 实际地址 | 就绪结果/检查时间 | PID/容器 ID/日志 | 收尾状态 |
|---|---|---|---|---|---|---|
（local 必需服务未就绪则相关链路 BLOCKED，记录缺失服务/失败阶段/超时及建议步骤，
立即对话提示用户，不自行修改代码/启动脚本/配置或修复已有服务。
记录提示内容、用户处理状态和复查结果。
准备证据不等于业务 PASS；existing 构建项记“不适用”，版本未知如实注明。
停止本轮启动服务，复用服务保持原状态；保留运行需记录停止方法。）

## 9. UI 录像与人工核对（有 UI 自动化时必填）
| 场景/环境/尝试 | 视频链接 | 关键步骤/时间点 | 实际节奏 | 自动断言结果 | 人工核对状态/反馈 |
|---|---|---|---|---|---|
（视频用相对路径，如 [订单录屏](videos/147/order/1/<实际文件>.webm)，
保留所有参与页面及失败尝试，步骤时间线存同目录 steps.json。
人工状态：待核对/已核对/有问题/证据缺失；待核对同步列人工清单，
未取得实际反馈不得标已核对。录屏证据缺失须单列，不能以截图/trace 代替。
HTML 保留相同相对视频链接，移交时视频目录需与报告一起保存。）
```

## 三、对账断言标准（判定 PASS 的最低门槛）

| 场景 | 必须断言到 | 不算通过的反例 |
|---|---|---|
| E2E 业务流程 | 从真实页面/API/消息/任务入口触发，关联同一业务标识，核对最终业务结果和必要副作用 | 只打开页面、只调用健康检查、仅靠 mock 或直接改 DB 后查到记录 |
| 延迟/异步链路 | 触发后**轮询断言**：明确等待窗口与轮询间隔（如每 5s 查一次、最长 3min），到窗仍未生效才判 FAIL | "过了一会儿好像生效了" |
| 消息链路 | 发出的 messageId 在出口消息/落地记录中对上；routeKey、属性 key、值逐字段一致 | "队列收到消息了" |
| DB 副作用 | 改前查、改后查，精确到值与行数；条件更新场景断言不重复翻转 | "接口返回 200" |
| 扇出/广播 | 应到 N 条、实到 N 条，逐接收方核对 | "大部分都收到了" |
| 缓存 | 键存在性 + 值 + TTL；失效场景断言下一条消息即用新值 | "缓存里有东西" |
| SQL 改写 | EXPLAIN 走索引/兼容 ONLY_FULL_GROUP_BY 实测执行 | "SQL 语法没问题" |
| 性能 | 速率、错误数、资源上限推导（如 unacked ≤ 消费者数 × prefetch） | "感觉变快了" |

通用规则：

1. **L0 证据**（仅 HTTP 200、返回非空、页面可访问）只能记为诊断证据，不得标 PASS
2. **测试输入样本与预期值都在执行时从目标环境 DB 现查**（挖掘 SQL 见 05-test-data.md），
   禁止硬编码 ID/SN/样本值（业务数据是变化的）
3. 超过 JS 安全整数的 ID 一律按字符串处理（lib.js 已内置）
4. MQTT retained 消息：订阅会先收旧保留消息，断言必须带时间窗/去重
5. 证据要可复查：记录 messageId、查询 SQL、前后值快照，而不是"已验证"三个字
6. UI 自动化须全程录屏且节奏可人工查看；自动断言与人工视频核对分别记录，
   人工核对未完成不得将整轮 UI 验证总结为全部完成
