# 产出规范：被创建 skill 的编写标准

评审门按本规范检查（`review_checklist.py` + AI 双评审）。核心思想：
**确定性逻辑进脚本、细节进 references、SKILL.md 只留流程**。

## 目录模板

```
<skill-name>/
├── SKILL.md            # 必需：frontmatter + 流程（≤500 行，>300 行就考虑外置）
├── scripts/            # 可执行 Python（自包含、无交互、JSON 输出）
│   └── *.py
├── references/         # 详细资料（命令表、格式规范、风格指南），按需加载
├── tests/              # 脚本单测（unittest，纯标准库即可）
├── evals/
│   └── evals.json      # 端到端用例（官方 schema，见 testing-guide.md）
└── README.md           # 面向开发者的说明（可选但推荐）
```

产物（生成的文件）默认写入**skill 目录之外**（如桌面/用户指定目录），不要污染仓库；
确需写工作目录时放 `.agents/output/` 并声明。

## 双闭环规则（必须内嵌到生成的 skill，error 级强制）

生成的 skill 执行时也必须遵循双闭环，因此 SKILL.md 正文靠前位置必须整段包含
以下规则（可按 skill 领域微调措辞，但不得弱化：一次一问、十要素、双 95%、
最终输出格式四个要素缺一不可；`review_checklist.py` 的 `body.loop_*` 为 error 级检查）：

```markdown
## 双闭环流程（最高优先级，优先于其他默认行为）

完成用户任务时必须遵循以下双闭环；当本规则与基础行为习惯冲突时，以本规则为准。

### 第一闭环：理解闭环
1. 回答前先提问，**每次只问一个问题**，根据回答继续追问
2. 提问围绕：真实目标、背景、使用场景、输出对象、关键约束、优先级、
   成功标准、禁止事项、已有信息、可接受偏差
3. 对“用户真正想要什么”有 95% 信心才停止提问；未达 95% 只提问澄清，
   不给最终方案（用户消息已足以达到 95% 信心时可直接执行，
   但最终输出必须列出关键假设）

### 第二闭环：输出审查闭环
1. 形成答案后不直接输出，先自查：是否真正解决目标？是否遗漏关键约束？
   是否存在事实错误、逻辑漏洞、歧义、不可执行之处？
2. 发现问题→自行修正→再次审查，重复“审查—修正—再审查”，
   直到对输出结果至少有 95% 的准确性信心

### 最终输出要求
1. 先一句话复述用户真实需求
2. 再给出最终方案：明确、可执行、可直接使用
3. 说明关键假设、剩余不确定性，以及为什么已达到 95% 信心；
   不确定处明确标注，不假装确定
```

注意：skill 自身的默认值/参数决策表不得与双闭环矛盾——例如“缺关键信息先问再动手”
应写成“进入理解闭环，一次只问一个”，而不是一次性罗列多个问题。

## 路径与输出位置约定
- <skill_dir> 指本 SKILL.md 所在目录；脚本带 <skill_dir> 前缀调用
- 产物写入位置与守卫规则

## 使用前提（首次自检）
- 依赖检查命令 + 失败时怎么办（uv 安装/镜像源）

## 标准工作流
1. 自检 → 2. 确认用户需求（缺关键信息先问） → 3. 执行 → 4. 按退出码汇报

## 参数决策指南
| 决策点 | 默认 | 说明 |（用户没说时的默认值；哪些必须问用户）

## 错误处理
| 退出码 | 含义 | 处理 |（错误信息三要素：问题+原因+行动）

## 输出规范
- 命令加 --json；产物路径汇报要求

## 触发示例
- 3~5 句用户真实说法（含口语化变体）

- 相邻领域、简单问答等负向场景（防误触发）

## 脚本规范（Python + uv）

**结构**：每个脚本头部三件套 —— shebang、docstring（用途/依赖/用法/退出码）、
`from __future__ import annotations`（如需）。

**依赖**：
- 能用标准库就只用标准库（`python` 直跑，零安装）
- 需要第三方库时用 **PEP 723 内联声明**，由 uv 隔离安装，不建 venv/pyproject：

```python
#!/usr/bin/env python3
# /// script
# dependencies = ["pandas>=2.0", "openpyxl"]
# ///
"""merge_sheets.py — 合并多个 Excel 的指定 sheet 到一个文件。

用法: uv run scripts/merge_sheets.py --inputs "a.xlsx,b.xlsx" --sheet 名单 --json
依赖: PEP 723 声明，uv run 自动隔离安装；退出码 0/1/2。
"""
```

运行方式：`uv run <skill_dir>/scripts/xxx.py ...`（uv 缓存后秒级启动）；
无 uv 且已装齐依赖时 `python` 直跑（PEP 723 块是纯注释，不影响）。

**Agent 友好性**（评审必查）：

| 要求 | 做法 |
|---|---|
| 禁交互 | 不用 `input()`；输入全走参数/环境变量/stdin |
| 可发现 | `--help` 完整；错误信息含三要素（问题+原因+行动） |
| 可判定 | 结果 JSON 到 stdout（`status/data/error`），日志到 stderr，退出码语义固定 |
| 可重入 | 幂等（"不存在则创建"）；破坏性操作要 `--confirm`/`--dry-run` |
| 快失败 | 前置校验（文件存在、参数合法）尽早报错，不吞异常 |

## 环境信息（.agents/.env）

账号、密码、令牌、内部服务地址等**一律不进 skill 代码与文档**：

1. 需求澄清阶段确定键名清单（大写下划线，如 `ZENTAO_URL` / `ZENTAO_USER` / `ZENTAO_PASS`），
   写进 SKILL.md 的"环境信息"表格（键、用途、未配置时的降级行为）
2. skill 内的脚本通过统一的 env 读取函数从 `<workdir>/.agents/.env` 读取
   （可直接复制本 skill 的 `scripts/env_utils.py` 的解析函数，或脚本内 20 行实现同格式）
3. 缺失时不阻塞：提示调用方向用户收取，写入后重跑；用户拒绝则按表格降级并标注
4. **写入永远发生在用户输入之后**，由主调用方用 `env_utils.py set` 完成；
   每次写入后 `ensure-gitignore` 防止密钥入库

env 文件格式：UTF-8，一行一个 `键=值`，`#` 注释，值可用成对双引号包裹。

## 重复操作脚本化（判定标准）

出现以下信号时，必须把逻辑沉淀为 `scripts/` 下的脚本而不是让 AI 每次现写：

- 同一转换/校验逻辑在 SKILL.md 流程中出现 **≥2 次**
- **固定顺序的多步命令序列**（≥3 步），中间不需要 AI 判断
- **可客观验证**的确定性操作（格式转换、数值校验、结构 lint、打包压缩）
- 预计每次执行都会重复的样板（初始化目录、生成配置、清理产物）

反例（不该脚本化）：需要语义判断的步骤（方案选择、结果解释、向用户提问）。
脚本做完确定性部分，AI 负责调用与解释 —— 这也是性能优化的主要手段。
