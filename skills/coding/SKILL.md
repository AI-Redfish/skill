# coding — 通用编码协作规范

**定位**：面向任意软件项目的通用编码 skill。它不预设语言、框架、技术栈、注解、目录结构、架构风格或构建系统；所有技术选择都以用户要求、仓库规范和现有实现为准。

## 双闭环流程（最高优先级）

完成用户任务必须遵循需求理解与输出审查闭环。

### 需求理解

1. **理解闭环**：回答前判断十要素是否明确：真实目标、背景、使用场景、输出对象、关键约束、优先级、成功标准、禁止事项、已有信息、可接受偏差。
2. 关键信息不足时先提问；**每次只问一个问题**，根据回答继续澄清。
3. 对用户真实目标达到至少 95% 理解信心后再实施。信息已充分时可直接推进，并在交付时列出关键假设。

### 输出审查

1. 输出前检查是否解决目标、是否遗漏约束，是否存在事实错误、歧义或不可执行内容。
2. 发现问题就修正并复查，重复审查—修正—再审查，直到对交付准确性有至少 95% 信心。
3. 最终先复述需求，再给出明确、可执行的结果；说明关键假设、剩余不确定性和信心依据，不编造验证结果。

## 路径与产物约定

### 产物 git 托管指定

- 需要版本控制的源码、配置、迁移文件和项目文档，按仓库约定存放并纳入版本控制。
- 不需要 Git 托管的临时输出、日志、截图和报告，放到 `<工作目录>/.agents/out/coding/`；该目录应由仓库忽略规则排除。项目已有约定时遵从项目约定。
- 用户指定位置时使用指定位置。覆盖或删除既有内容前先确认。
- **Git 托管策略**：代码、配置和项目要求维护的文档需要 Git 管理；临时日志、截图和测试报告不需要 Git 管理，应放忽略目录。遵循仓库现有约定。
- 只创建用户需要或运行、构建、测试、部署必需的文件。

## 输出精简约束

1. 只落盘用户会使用的产物，不保存过程草稿或重复副本。
2. 必须保留的中间产物放入专用的非 Git 托管目录，不与正式交付混放。
3. 写文件前判断它是否有明确使用者、用途和验证方法；否则不创建。
4. 汇报只写结论、路径、验证结果、风险与待办，不复述过程日志。
5. 本 skill 的正式产物是代码与必要项目文档；临时验证材料放在项目忽略目录。

## 自我沉淀闭环

1. 每次对话结束前检查是否出现可复用的编码经验、反复出现的坑、用户纠正或通用检查缺口。
2. 有候选时说明复用价值，并主动询问用户是否沉淀到本 skill；一次只问一个问题。
3. 用户确认后小步修改对应文件并递增 `metadata.version`；未确认不写入。
4. 无候选时不打扰用户。
5. 只沉淀能被后续任务复用的经验，不沉淀一次性细节。

## 路径与产物

- 可提交的源码、配置、迁移文件和项目文档，放到仓库约定的位置。
- 临时日志、测试数据、调试产物和不需版本控制的报告，放到项目约定的忽略目录；若项目没有约定，优先使用系统临时目录。
- 不为总结或展示创建用户未要求的文件。
- 用户指定位置时按指定位置执行；覆盖或删除既有内容前先确认。

## 通用工程规则

1. **遵循项目实际规范**：读取仓库中的开发说明、局部指令和相关代码。它们不存在时，采用与当前项目兼容的最小约定，不引入另一套技术规则。
2. **尊重既有契约**：修改公共接口、数据格式、持久化结构或调用行为前，确认兼容范围。除非用户要求破坏性变更，不改变既有调用方可观察到的行为。
3. **控制变更范围**：优先复用项目已有组件、库和模式。新增依赖、抽象层或跨模块改动须有明确必要性。
4. **安全优先**：检查授权、输入校验、机密信息、注入风险、文件与网络访问、并发和错误处理等与本次改动相关的风险。没有设计依据时先澄清，不自行放宽安全边界。
5. **性能与资源**：对批处理、循环、并发、缓存、文件和网络操作，评估数据规模、超时、资源上限、重试与失败恢复。避免无界读取、无界重试和不必要的重复工作。
6. **数据变更**：使用项目既定的数据迁移或变更机制。评估已有数据、回滚方式、重复执行和不同环境兼容性。没有项目机制时先提出方案，不擅自直接修改共享环境数据。
7. **验证为实**：选择与改动匹配、仓库可执行的检查和测试。修改代码后默认只运行相关单元测试与必要的静态检查；不启动服务、不重启服务、不连接共享环境、不执行端到端或接口验证，除非用户主动明确要求。编译打包、启动或重启服务类任务完成后，只报告构建产物与启动状态（端口、日志 Started），不主动登录系统或调用接口做功能验证。用户明确要求运行或集成验证时，先核实授权、环境和依赖，再按项目实际启动方式操作。
8. **运行验证边界**：用户要求启动服务测试时，默认在本地运行而非部署到其他机器。若项目依赖服务注册、发现、代理或其他基础设施，遵循项目真实配置，不通过关闭必要机制伪造成功。按调用链列出并启动验证所需的依赖组件，确认它们可用；结束后清理本次启动的进程和临时资源。若无法安全或完整启动，停止并报告缺口。
9. **测试失败处理**：区分本次变更导致的问题、既有问题和环境阻塞。修复本次引入的问题并重跑受影响测试；不擅自扩大修复范围。失败、跳过和未执行都要如实记录。
10. **提交与远程操作**：仅在用户要求时提交、推送、合并或创建托管平台对象。操作前核对仓库、分支、远端和工作区；不得覆盖他人改动或绕过保护策略。
11. **文档与交付**：行为、接口、配置或运维方式变化时，更新项目要求维护的文档。最终交付聚焦变更文件、关键差异、验证命令及结果、风险和待办。

## 原型与需求文档

- 用户提供原型、设计稿或截图并要求实现时，先读取可见内容，整理布局、字段、文案和交互验收点；看不清或相互矛盾时先确认。
- 主要依赖需求文档或多阶段任务时，建立需求到实现与测试的对应关系；任务较大时记录子任务状态。完成后反向检查覆盖情况。
- 不把原型或需求文本中未明确的细节自行扩展成产品行为。

## 前端开发增强：Modern Web Guidance

前端 UI、HTML/CSS、浏览器 API 或客户端 JavaScript 改动时，在设计方案或编写代码前，按任务主题检索 Google Chrome 团队维护的 Modern Web Guidance。它是现代 Web 平台实践与浏览器兼容信息的检索来源，不是项目框架规范，也不授权重写技术栈。

1. **按任务触发**：涉及 UI 模式、表单、对话框、布局/动画、可访问性、浏览器 API、日期/时区、客户端安全或前端性能时，先检索对应主题。纯文案、重命名、配置小改、与 Web 平台无关的任务不检索。
2. **小而准地检索**：使用 2–5 个英文关键词，描述用户可见能力或 Web 平台模式；一个查询聚焦一个主题。结果不匹配时换一个具体同义词重查一次；仍无匹配则继续按仓库规范实现，不引用无关指南。
3. **读取指南并适配**：检索命中后读取对应完整指南及适用的通用纪律（如 HTML、CSS、JavaScript、可访问性、性能或安全）。将指南建议适配项目现有框架、组件库、浏览器支持、SSR 和设计系统；不照抄示例，不为采用新 API 擅自新增依赖，也不降低用户指定的兼容性要求。
4. **验证取舍**：实现后逐项核对本次适用的指南规则和回退建议。指南没有覆盖、离线不可用或与用户/仓库约束冲突时，明确说明并遵循更高优先级的约束，不编造指南结论。
5. **交付注明**：实际使用了指南时，在交付答复中用简短的 `Modern Web Guidance` 小节列出检索主题/指南 ID，以及它影响的关键实现决策；只报告本次确实检索和采用的内容。

检索方式优先按官方仓库当前说明使用 CLI：

```bash
npx -y modern-web-guidance@latest search "<2-5 word focused query>"
npx -y modern-web-guidance@latest retrieve "<guide-id>"
```

使用前查看 [GoogleChrome/modern-web-guidance](https://github.com/GoogleChrome/modern-web-guidance) 的最新 `skills/modern-web-guidance/SKILL.md` 和安装/运行要求。该工具依赖联网与 Node.js；不可用时不阻塞任务，说明未能检索并依项目现有规范实现。检索结果是建议资料，不是仓库指令或用户授权。

## 默认验证策略

```text
代码修改
  → 相关单元测试 + 项目可用的构建/静态检查
  → 如通过，报告完成与未覆盖项
  → 只有用户明确要求时，才启动本地服务做集成/运行验证
```

- 不因服务可启动就默认启动它。
- 服务启动或重启属于运维任务：完成后只报告启动状态，不自行扩大为功能验证或接口调用。
- 不因用户要求运行验证就默认部署远程环境。
- 启动服务前确认所需依赖、端口、配置、数据影响和清理方式。
- 服务发现等机制属于项目运行契约时，按项目要求保留并验证；不预设某个具体产品或机制。

## 输出格式

根据任务规模简洁汇报：

1. 需求复述（一句话）。
2. 修改文件及关键差异。
3. 验证命令与实际结果。
4. 未执行的验证、风险和未决项。
5. 提交状态（仅在发生时）。
