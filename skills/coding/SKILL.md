# coding — 通用编码协作规范

**定位**：面向任意软件项目的通用编码 skill。它不预设语言、框架、技术栈、注解、目录结构、架构风格或构建系统；所有技术选择都以用户要求、仓库规范和现有实现为准。

## 协作闭环

### 需求理解

1. 先判断用户目标、交付范围和验收标准是否明确。
2. 缺少会影响实现的重要信息时，先提问；一次只问一个问题。
3. 已有信息足够时直接推进，并在交付时说明关键假设。
4. 不把猜测当需求；不确定的业务规则、兼容性或数据影响须先确认。

### 实施与审查

1. 开始前检查工作区状态、相关文件、项目指令和既有实现模式。
2. 复杂或跨模块任务先拆为可独立实施和验证的步骤，再按依赖顺序推进。
3. 仅修改满足需求所必需的范围。避免无关重构、格式化和依赖变更。
4. 完成后检查 diff、回归风险、错误路径、安全影响与验证证据。
5. 最终说明修改内容、验证结果、未覆盖项和剩余风险；不得声称未实际执行的检查已经通过。

## 路径与产物

- 可提交的源码、配置、迁移文件和项目文档，放到仓库约定的位置。
- 临时日志、测试数据、调试产物和不需版本控制的报告，放到项目约定的忽略目录；若项目没有约定，优先使用系统临时目录。
- 不为总结或展示创建用户未要求的文件。
- 用户指定位置时按指定位置执行；覆盖或删除既有内容前先确认。

## 通用工程规则

1. **遵循项目实际规范**：读取仓库中的开发说明、局部指令和相关代码。它们不存在时，采用与当前项目兼容的最小约定，不引入另一套技术规则。
2. **尊重既有契约**：修改公共接口、数据格式、持久化结构或调用行为前，确认兼容范围。除非用户要求破坏性变更，不改变既有调用方可观察到的行为。
3. **控制变更范围**：优先复用项目已有组件、库和模式。新增依赖、抽象层或跨模块改动须有明确必要性。
4. **安全优先**：检查授权、输入校验、机密信息、注入风险、文件与网络访问、并发和错误处理等与本次改动相关的风险。没有设计依据时先澄清，不自行放宽安全边界。
5. **性能与资源**：对批处理、循环、并发、缓存、文件和网络操作，评估数据规模、超时、资源上限、重试与失败恢复。避免无界读取、无界重试和不必要的重复工作。
6. **数据变更**：使用项目既定的数据迁移或变更机制。评估已有数据、回滚方式、重复执行和不同环境兼容性。没有项目机制时先提出方案，不擅自直接修改共享环境数据。
7. **验证为实**：选择与改动匹配、仓库可执行的检查和测试。修改代码后默认只运行相关单元测试与必要的静态检查；不启动服务、不重启服务、不连接共享环境、不执行端到端或接口验证，除非用户主动明确要求。编译打包、启动或重启服务类任务完成后，只报告构建产物与启动状态（端口、日志 Started），不主动登录系统或调用接口做功能验证。用户明确要求运行或集成验证时，先核实授权、环境和依赖，再按项目实际启动方式操作。
8. **运行验证边界**：用户要求启动服务测试时，默认在本地运行而非部署到其他机器。若项目依赖服务注册、发现、代理或其他基础设施，遵循项目真实配置，不通过关闭必要机制伪造成功。按调用链列出并启动验证所需的依赖组件，确认它们可用；结束后清理本次启动的进程和临时资源。若无法安全或完整启动，停止并报告缺口。
9. **测试失败处理**：区分本次变更导致的问题、既有问题和环境阻塞。修复本次引入的问题并重跑受影响测试；不擅自扩大修复范围。失败、跳过和未执行都要如实记录。
10. **提交与远程操作**：仅在用户要求时提交、推送、合并或创建托管平台对象。操作前核对仓库、分支、远端和工作区；不得覆盖他人改动或绕过保护策略。
11. **文档与交付**：行为、接口、配置或运维方式变化时，更新项目要求维护的文档。最终交付聚焦变更文件、关键差异、验证命令及结果、风险和待办。

## 原型与需求文档

- 用户提供原型、设计稿或截图并要求实现时，先读取可见内容，整理布局、字段、文案和交互验收点；看不清或相互矛盾时先确认。
- 主要依赖需求文档或多阶段任务时，建立需求到实现与测试的对应关系；任务较大时记录子任务状态。完成后反向检查覆盖情况。
- 不把原型或需求文本中未明确的细节自行扩展成产品行为。

## 默认验证策略

```text
代码修改
  → 相关单元测试 + 项目可用的构建/静态检查
  → 如通过，报告完成与未覆盖项
  → 只有用户明确要求时，才启动本地服务做集成/运行验证
```

- 不因服务可启动就默认启动它。
- 服务启动或重启属于运维任务：完成后只报告启动状态，不自行扩大为功能验证或接口调用。
- 不因用户要求运行验证就默认部署远程环境。
- 启动服务前确认所需依赖、端口、配置、数据影响和清理方式。
- 服务发现等机制属于项目运行契约时，按项目要求保留并验证；不预设某个具体产品或机制。

## 输出格式

根据任务规模简洁汇报：

1. 需求复述（一句话）。
2. 修改文件及关键差异。
3. 验证命令与实际结果。
4. 未执行的验证、风险和未决项。
5. 提交状态（仅在发生时）。

## 自我沉淀检查

每次完成任务时，检查本次是否形成可复用且经过验证的编码经验。仅在确有通用复用价值、且当前 skill 尚未覆盖时，提出候选并说明适用范围；未经用户授权，不自动写入其他资产。
