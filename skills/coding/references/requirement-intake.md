# 开工前准入门禁（吸收 bps-rd-intake-gate 硬门禁 + 会话经验）

> 编码前判断需求是否可进入实现。任一阻断项命中：只实现已确认部分并暂停提问，不抢跑。

## 硬性阻断（任一命中先向用户澄清，一次一个问题）

1. 业务归属和模块边界不清，无法决定放在哪个服务/模块。
2. 写入数据、主键、唯一性、逻辑删除、历史引用规则不清。
3. 对外接口、页面调用、异步消息或第三方依赖边界不明。
4. 权限码、数据权限、租户/院区/组织/角色口径无法落地。
5. 无法构造 P0 验收路径和至少一条负向测试路径。
6. 涉及存量数据或兼容变更，但没有迁移、回滚或灰度策略。
7. 业务口径细节不明：标签编码、接口路径、状态码集合、过滤作用于存量还是查询等。

## 会话实战补充（非 BPS 标准项，但同样阻断）

- 需求表述与现有实现可能冲突时（如"接口要通用"vs 已有专用参数），先确认改造方向再动手。
- 涉及多方共用接口时，确认"其他调用方是否允许行为变化"，默认答案是"不允许"。
- 历史数据处理方式（自动任务 / 手动 SQL / 不处理）必须确认，不得默认。

## Think First 四问（动手前必须能回答）

| 检查项 | 通过标准 |
| --- | --- |
| 目标 | 能用 1-2 句话说清本次要交付的行为变化 |
| 范围 | 能列出要改和不要改的文件/模块边界 |
| 依据 | 每个接口、表、状态、权限变化都能指向需求或用户确认 |
| 测试 | 每个高风险点都有验证方式 |
