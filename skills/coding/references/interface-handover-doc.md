# 前端接口交接文档分册（页面分组接口文档）

> 本分册支持两种模式，生成前先确认受众：
> **模式 A：开发对接向**——提给前端开发者人工对接（需求开发完成后的接口交付）。核心是**完整参数表（字段名/类型/必填/含义/字典编码）、新增/改造/复用状态标注、派生枚举表、对接注意事项、PC+移动端双端覆盖**；规范见第 10 节。
> **模式 B：自动化凭证向**——面向前端 AI 与接口/UI 自动化测试的交付文档：按“页面 → 模块/区域 → 按钮/操作 → 接口”四级分组，核心是**接口依赖与字段取值映射（自动化凭证）**与**字典关联**；规范见第 2—9 节。
> 两模式共用：第 1 节触发条件、第 2 节输入（含前端仓库）、第 3 节分析步骤、第 7 节 URL 识别。
> 与硬性约束 11 的关系：小改动用简版交接文档（修改前后对照）即可；接口变更多、前端对接复杂时升级为本分册完整文档。

## 1. 何时生成（条件触发）

- 本次需求新增/变更 Controller 接口且前端需要对接（页面新增、按钮行为变化、字段增减）
- 用户明确要求“生成接口文档 / 接口清单 / 前端对接文档”——默认为**模式 A（开发对接向）**；明确说明给自动化测试脚本消费时用模式 B
- 接口将被接口自动化 / UI 自动化脚本消费 → 模式 B
- 需求含纯前端展示改造（无后端改动但前端需要上下文）→ 模式 A，以附录形式说明（见 10.7）

单个接口加可选参数等小改动 → 用硬性约束 11 简版交接文档，不升级。

## 2. 输入

1. 当前仓库增量代码：`git status` / `git diff` 识别本次变更的 Controller、DTO、VO、Service、Mapper；**若需求已在工作区实现，直接读工作区代码（未提交也算实现）**
2. 前端仓库路径：读相关页面 `api.js` / api 模块，**实证前端实际调用的 URL**（比后端注解更接近事实：可发现死代码接口、前后端路径不一致、实际调用的是哪个方法）；无前端仓库时标“前端对账待实施”
3. PRD：用户指定路径；未指定时在 `.agents/`、`docs/`、需求相关目录查找。
4. PRD 原型：HTML/图片，补充页面名称、模块/区域、按钮、列表/详情/弹窗/抽屉界面事实。
5. Swagger 地址：用户执行时提供；未提供则提示一次，明确不提供则文档顶部留空，**不猜测、不拼接**。

## 3. 分析步骤

1. 读 PRD：提取页面、页面模块/区域、功能点、按钮/操作入口、页面关系。
2. 读原型：补充界面事实与命名。
3. 查增量：`git status` + `git diff` 定位新增/变更的 Controller 路由；需求已实现时以工作区代码为准。
4. **前端 api.js 实证（模式 A 必做，本次实战验证价值极高）**：在前端仓库按页面目录读 `api.js`/api 模块，提取页面实际调用的 URL——可发现：①后端不存在的死代码接口（标注“勿用”）；②前后端路径不一致（疑似网关重写，列对接前核对项）；③同一语义在不同接口参数名不同（如空间过滤一处叫 `spaceIdList`、另一处叫 `locationIds`，必须按各页签如实标注，不得统一改名）；④仅移动端存在的接口（如 `changeTask` 仅 app 前缀）。
5. 补复用既有接口：PRD/原型的页面加载、查询、详情、下拉选择、关联弹窗、编辑回显、删除确认、导出等交互需要的**既有接口**，即使不在本次 diff 内也必须纳入，并在代码中查找 Controller 路由确认；不能确认完整 URL 时标“待确认”。
6. 三级归属：接口归入 PRD 页面（一级）→ 页面模块/区域（二级，PRD 未明确时用“默认模块”）→ 按钮/操作入口（三级：页面加载、查询、查看详情、新增、编辑、删除、批量删除、下拉选择、编辑回显等，非按钮触发的按实际操作入口命名）；弹窗/抽屉/子表接口归承载它的页面；无法确认页面归“待确认页面”并标注。PC 与移动端分别成章（移动端含 h5 页面目录与 app 前缀接口）。
7. 所属后端模块：用 Swagger 地址同主机的 `/v3/api-docs/swagger-config`，从响应 `urls[]` 中取 `urls[].url` 去掉 `/v3/api-docs` 及查询参数后的业务前缀，与接口 URL 做**最长前缀匹配**，取该 `urls[].name`（示例：`/api/monitor/video/device/list` 匹配 `/api/monitor/v3/api-docs?group=default` 的前缀 `/api/monitor`，模块写“监测中心”）。无法访问、无 `urls` 或无匹配写“待确认”；**不按代码路径硬编码推断模块名**。
8. 接口依赖与字段取值映射（模式 B）：见第 5 节。
9. 字典整理（模式 B；模式 A 只在参数表标字典编码与 DictMap 字段）：见第 6 节。
10. 生成 Markdown 按模式写入约定路径（模式 A 常为用户指定桌面/交付目录；模式 B 写入 `.agents/out/coding/`）。

## 4. 输出格式与路径

文件：`.agents/out/coding/{{需求名称}}接口文档.md`（属用户直接使用的交付物，非 git 托管产物目录，不受"不落盘"约束）。顶部必含 `Swagger 地址：`行。

```markdown
# {{需求名称}}接口文档

Swagger 地址：{{swaggerUrl}}

## {{页面名称}}

### {{页面模块/区域名称}}

#### {{按钮/操作入口名称}}

##### {{接口名称}}

- 接口作用：{{一句话说明}}
- 应用页面：{{页面名称，多页面复用列多个}}
- 页面模块：{{页面模块/区域名称}}
- 触发按钮/操作：{{按钮/操作入口}}
- 所属后端模块：{{swagger-config 匹配的中文模块名}}
- URL：`{{具体接口 URL}}`
- 接口依赖与字段取值映射：{{见第 5 节}}
- 接口关联字典：{{见第 6 节}}
```

分组规则：

- 严禁按 Controller / Java 类 / 数据库表分组
- 一个按钮调多个接口 → 同一操作入口下并列列出
- 同一接口多入口复用 → 放最主要入口，"触发按钮/操作"注明复用关系
- 同模块按钮按页面操作顺序排列：页面加载、查询/搜索、详情、新增、编辑、删除、批量、关联操作、导出

## 5. 接口依赖与字段取值映射（核心，每接口必含）

无前置依赖写"无前置接口依赖"，并说明是否仅依赖用户输入、默认值或登录上下文。

必须写清五件事：

1. **前置依赖**：调用前必须先调用哪些接口
2. **依赖原因**：提供页面选项 / 列表选中行 / 详情回显 / 业务主键 / 外键 / 类型值 / 状态值 / 字典值 / 租户上下文 / 测试数据准备
3. **取值路径**：`接口 URL + 响应字段路径`，如 `/api/xxx/list` 的 `data.dataList[0].id`
4. **映射目标**：当前接口请求字段名，标注必填/可选与取值约束
5. **自动化凭证**：脚本如何稳定构造该值——先调用列表取第一条、先新增可删除的测试数据、字典用固定项、批量从列表取多个 ID、页面选中行；数据可能为空时注明需预置

常见映射场景：

- 新增依赖下拉/选择弹窗：`下拉或列表接口的 id/code/type` → 新增接口外键/类型字段
- 编辑依赖详情：`详情返回字段` → 保存接口同名或业务等价字段，主键单独说明
- 删除依赖列表：`列表选中行 id` → 删除接口 `id`；批量：多条 `id` → `ids`
- 绑定/关联依赖双方：`主对象 id` + `选择弹窗对象 id` → 绑定接口对应字段
- 执行/启停/状态流转依赖当前 `status`（决定按钮可点）+ `id` 映射到操作接口
- 字典/常量值：固定字典项 `value` → 当前接口类型、状态、分类字段

响应结构无法确认时写"响应路径待确认"，不脑补。

## 6. 字典整理

- 从 Controller 方法定位 Service → 查询/详情返回的 Model/VO/DO，以及 `getByIdWithRelation`、`get*ListWithRelation`、`MyRelationParam.full()` 等关系填充对象
- `@RelationGlobalDict`：只输出 `dictCode`（如 `AlarmLevelDict`），**不输出字典项**
- `@RelationConstDict`：输出 `constantDictClass` 类名、关联字段和具体字典项（如 `MonitorTypeDict`：`objectType`，字典项：`0-设备`、`1-空间`）；字典项必须从常量字典类中读取，不只写类名
- 同一接口关联多个返回对象/明细对象时合并去重写在接口下；不同接口分别说明，不在模块顶部汇总
- 普通 `@RelationDict`、`@RelationOneToOne`、`@RelationOneToMany` 不作为字典输出（除非其关联对象自带上述字典注解且随接口返回）
- 未发现字典写：`接口关联字典：未发现`

## 7. URL 识别

- Controller 类基础路径 + 方法注解路径拼接完整 URL；只输出具体业务 URL
- 不输出 Java 方法名代替 URL；不输出不完整路径（只能确认部分时写"待确认"并说明缺哪级）；不编造 URL

## 8. 禁止输出

- 与接口依赖、取值映射、自动化准备无关的完整字段/请求参数/响应参数说明（不做 Swagger 式字段展开）
- 请求方法、Content-Type、权限码、Controller 类名等详细信息（用户明确要求除外）
- Swagger 自动生成的 schema 内容

## 9. 模式 A：开发对接向文档规范（前端人工对接）

面向前端开发者的接口交付文档。与模式 B 的根本差异：**必须给出完整参数表**（字段名/类型/必填/字段含义/字典编码），而非自动化凭证；核心是让前端不经追问即可完成对接。

### 10.1 文档结构（按前端页面/端组织，不按 Controller 分组）

1. 文档头：版本、日期、后端分支、涉及前端仓库与应用
2. 基础约定：Method 风格、`@MyRequestBody` 组合入参说明、`ResponseResult` 包装与错误结构、分页结构（`MyPageData{rows,total}`）、`pageParam` 上限、`字段名+DictMap` 字典回填风格
3. **接口总览表**：按前端页面分组列出全部涉及接口，标注【新增】/【改造-新增字段或参数】/【复用-无变化】，前端一眼识别本次变化
4. 各页面分节：每个接口独立成段——URL/Method/入参表/响应结构/权限码/错误提示文案/对接注意事项
5. 派生枚举表：后端派生的聚合状态（前端直接按值展示）逐值列「取值 | 含义 | 判定口径（后端派生）」
6. 嵌套结构：列表/数组元素的完整字段表（如 captures[] 逐字段）
7. 附录：无后端改动的纯前端展示改造说明（按既有契约提交、前端裁剪/拼装、组件控制上限等），让前端理解上下文

### 10.2 必写内容（实战验证的易漏点）

1. **状态标注三分类**：【新增】/【改造-新增字段或参数】/【复用-无变化】——总览表与各接口节都要标
2. **完整参数表**：入参与响应均用表格（字段名、类型、必填、含义、字典编码）；响应扩展接口只列新增字段并声明「其余不变」
3. **派生枚举表**：后端派生的聚合状态逐值给判定口径，并注明「不落库、后端推导、前端直接按值展示」；若含异步进行中状态（如 TAKING）必须写「不要轮询阻塞，刷新/重进可见」
4. **快照语义**：留存名称/路径类冗余字段注明「历史快照，源数据改名/解绑后不变」；图片类注明附件 JSON 解析方式与鉴权
5. **异步链路**：触发时点、生成后可见时机、幂等键、失败处理（部分成功保留成功数据）
6. **死代码标注**：前端 api.js 中后端不存在的接口明确标「勿用」
7. **前后端路径不一致**：列「对接前核对」项（疑似网关重写时注明），不猜测路由归属
8. **参数名不一致如实写**：同一语义在不同接口的参数名不同时，按各页面/页签如实标注，不得统一改名
9. **双端覆盖**：PC 与移动端分别成章；移动端逐接口列全（含复用）；仅移动端存在的接口（如 changeTask 仅 app 前缀）注明，PC 无对应接口时写清对接选项
10. **交互约定**：多选弹窗「确认仅回填、查询才生效」、页签切换保留已选、重置语义等逐条写清

### 10.3 实证要求

- 所有 URL、字段名、权限码、错误文案均从**当前后端代码**提取（Controller 注解 + DTO/VO 字段 + @Schema/@SaCheckPermission），不从文档设计稿转抄；文档设计与代码不一致时以代码为准并在文档注明
- 前端实际调用路径以前端仓库 api.js 为准；两者冲突时列入「对接前核对」
- 交付格式：Markdown + HTML（离线可读）配对；输出路径按用户指定（常为桌面等交付目录）

## 10. 交付前自检

**模式 B（自动化凭证向）自检**：
- 文件在 `.agents/out/coding/`，顶部含 `Swagger 地址：`行
- 覆盖范围 = 增量接口 + PRD/原型确认复用的既有接口（不是只有 diff）；PRD 有页面但 diff 无接口时先查复用，确认没有才写"本次增量代码未发现新增/变更接口，且未从 PRD/原型确认复用既有接口"
- diff 有接口但 PRD/原型找不到页面 → 归"待确认页面"
- 四级标题结构正确（页面/模块/操作入口/接口）；每个接口八要素齐全
- 每个写操作接口说明主键、外键、类型、状态、父级 ID、关联对象 ID、批量 ID、编辑回显字段的来源接口、响应路径与映射目标
- 每个接口有可落地的自动化凭证；字典规则正确（全局只有编码、常量有类名+字典项）
- 所有不确定信息标"待确认"，不脑补

**模式 A（开发对接向）自检**：

- 按前端页面/端分章，接口总览表全覆盖（新增/改造/复用三分类标注完整）
- 每个接口含 URL、Method、完整入参表、响应结构（扩展接口列全新增字段）、权限码、错误文案、对接注意事项
- 派生枚举表逐值含判定口径；异步态已注明不落库与可见时机；快照字段已注明历史语义
- 前端 api.js 实证完成：死代码已标勿用、路径不一致已列对接前核对、参数名不一致已按页签如实标注
- 纯前端改造需求已入附录；PC 与移动端均已覆盖且移动端接口逐个列全
- 字段/URL/权限码/错误文案与后端代码逐一对账，无转抄自设计稿的过时内容
