# 任务拆分分册（大型需求先拆后做）

> 目标：把大型/多链路需求拆成可独立执行、可独立验证、防遗漏的子任务，再逐个进入编码；用本地任务跟踪文件持续记录完成状态，最后反向核对需求来源，降低遗漏风险。
> 拆分阶段只拆分、不写码；任务单交用户确认后，回到 SKILL.md 标准工作流逐任务执行。凡主要依据需求文档、技术文档、PRD、原型说明等文档开展开发，均必须拆分并落盘任务跟踪文件，不受第 1 节小型需求例外影响。

## 1. 何时拆分（命中任一即先拆，全不命中直接实现）

- 需求包含建表 SQL / 新表 / 新关联表（基础 CRUD 与后续业务要分批）
- 字段级改动横跨全链路（Flyway→Entity→DTO→VO→Mapper 接口→Mapper XML→Service→Controller→测试/文档）且叠加多个业务能力
- 含复杂业务流转接口动作：`submit` / `approve` / `reject` / `cancel` / `enable` / `disable` / `saveWithRelation` / `updateWithRelation` / 导入导出等
- 主表 + 关联表联动维护（新增/修改时同步维护子表，查看时回填）
- 需求覆盖多个页面/接口，单次实现难以收敛，或用户明确要求"先拆任务再实现"

全不命中且需求并非基于需求/技术/PRD 等文档 → 不拆分，直接按标准工作流第 4 步最小实现。基于上述文档开发 → 即使需求看起来较小，也要至少拆成可验收任务并落盘跟踪。

## 2. 拆分前先扫现有代码模式（禁止只看需求文本）

先通读同域模块的真实实现风格，任务拆分必须贴着项目既有模式：

- 同域或邻近模块的 Entity / DTO / VO / Mapper / Mapper XML / Service / Controller 写法
- 主表+关联表的既有处理模式：关联数据回填（withRelation 类）、保存/更新时关联数据维护、批量创建/更新、导出复用
- 字典、租户/院区/组织数据范围、逻辑删除、权限范围的既有处理方式
- Flyway 脚本命名与既有表结构风格

拆分依据是"项目里这类改动实际怎么落"，不是方案文本的抽象描述。

## 3. 需求提取清单（拆分前先整理事实底稿）

- 涉及的表、每表字段、新增/变更/删除字段、字段命名风险（别名、同名不同义）
- 主表字段 vs 关联表/中间表字段的归属
- 增量 SQL 类型：加字段 / 改字段 / 建表 / 建关联表；是否含初始化数据
- 影响面：列表查询、详情、保存、更新、导出、过滤条件；Mapper XML 自定义查询逐 statement 影响点（对齐硬性约束 16）
- 字典、租户/院区/组织、逻辑删除、权限范围是否受影响
- 接口动作清单：`list` / `view` / `add` / `update` / `delete` / `export` / 状态流转类动作
- 字段在链路各层的联动点：entity→dto→vo 转换、controller 装配、service 业务规则、XML 列片段/resultMap/insert/update/where

清单整理不出来或口径不明 → 按标准工作流第 2 步准入门禁提问，在任务单中标注"需确认项"，**不编造字段与规则**。

## 4. 拆分原则（七条）

1. 一个子任务 = 一个可独立执行、可独立验证的业务目标
2. 全链路字段联动保持在一个子任务内完成（对齐硬性约束 16），禁止把同一条链路拆成"只改 Entity""只改 XML"的碎片
3. 相互独立的业务流程拆成不同子任务，禁止把独立流程合并成巨型任务
4. 有新表时先拆**基础 CRUD 任务**（Flyway 双端 → Entity → DTO → VO → Mapper → XML → Service → Controller，按仓库模板），复杂业务任务全部后置；关联表视需要拆最小 CRUD 支撑任务
5. 复杂业务按接口动作拆，**一个动作一个任务**（`submit` / `approve` / `reject` / `cancel` / `enable` / `disable` 等各成任务），不合并成"业务流转大任务"
6. "新增并维护关联表"与"修改并维护关联表"通常拆成两个任务
7. 主子表任务必须显式检查四件事：DTO→Entity 转换覆盖关联数据、保存/更新落关联数据、详情/列表回填关联数据、删除时的关联处理

## 5. 子任务单格式（必须落盘 + 答复中摘要）

每个子任务必含：

| 字段 | 说明 |
|---|---|
| 编号 | T1、T2…（执行顺序即依赖顺序） |
| 标题 | 一个业务动作短语 |
| 类型 | 基础 CRUD / 字段联动 / 复杂业务 / 关联维护 / 导出 / Flyway / 测试配套 |
| 目标 | 一句话说清交付的行为变化（对齐 Think First"目标"） |
| 范围 | 预期改动的模块/文件/层（允许执行时按实际微调） |
| 前置依赖 | 依赖的子任务编号 |
| 验收点 | 可验证的检查项（含测试要求） |
| 风险点 | 兼容性/性能/数据行为风险 |
| 需确认项 | 拆分时无法裁决的口径（执行到该任务前必须澄清） |

任务单后必须附**覆盖映射表**：需求提取清单中的每个字段 / 关联表 / 接口动作 / 影响面（list、detail、save、update、export、filter、XML statement）→ 对应子任务编号。任何一项映射不到任务即拆分失败，必须补任务；字段名保持与方案原文一致，不改写、不归一化。

## 6. 本地任务跟踪文件（强制）

凡文档驱动开发或命中拆分条件，必须在开始编码前创建并维护一个任务跟踪文件：

- 路径：`<仓库>/.agents/out/coding/tasks/<需求短名>-task-tracker.md`；短名使用稳定、可读的 kebab-case，避免覆盖其他需求文件。
- `.agents/out/` 是本地产物，不提交 Git；若目录不存在则创建。不可写入仓库时必须先告知用户并暂停文档驱动的大型实现，不能只在回答里列任务替代。
- 文件包含：需求来源与版本/路径、目标与范围、需求提取清单、子任务表、依赖、验收点、风险/待确认项、覆盖映射表、进度日志、最终核对记录。
- 状态统一：`[ ] 未开始`、`[~] 进行中`、`[x] 已完成`、`[!] 阻塞`、`[-] 不适用（附理由）`。每项必须有唯一编号 T1…；验收点可独立核验。
- 开工前先写全任务、验收标准与覆盖映射，并向用户摘要说明任务计划；需要用户确认的，确认后才编码。用户要求直接执行时，也要先落盘计划，再开始编码，不跳过计划。
- 每完成一个子任务（实现 + 该任务要求的测试/验证均通过）立即更新其状态为 `[x]`，补充实际改动文件、验证命令/结果与完成时间；仅代码写完、测试未过不得标完成。任务开始时标 `[~]`；发现阻塞/新增范围即时记入文件并暂停相关工作。
- 发现需求遗漏、新联动或需求变更时，先更新任务/映射表，再继续；保留简短进度日志，禁止默默改计划导致追溯断裂。
- 最终交付前，任务表必须全部为 `[x]` 或有理由的 `[-]`；存在 `[ ]`、`[~]`、`[!]` 时不得声称需求整体完成。

## 7. 全部完成后的反向核对（强制，目标 ≥95% 把握无遗漏）

不能只看任务表打勾，必须从需求来源反向走查，形成可审计的核对记录：

1. **来源冻结**：核对采用的需求/技术文档路径、版本、章节/页码；检查引用的附件、补充说明、原型和用户确认记录是否都纳入。来源变更需明确版本并更新追踪文件。
2. **双向覆盖**：逐条从需求来源抽取原子需求（字段、规则、接口、页面/状态、权限、异常、非功能要求、验收标准），映射到任务编号、代码/文档位置、测试/验证证据；反向检查每个改动都能追溯到需求或经用户确认，识别范围外改动。
3. **实现核验**：逐任务核对验收点、改动文件、测试结果；字段/接口/页面/数据流等用相应专项清单复核。代码搜索结果、构建/测试日志路径或命令应记录为证据，不能用“看起来完成”替代。
4. **遗漏扫描**：检查文档中的表格、脚注、附件、流程分支、异常路径、权限/数据范围、非功能要求、明确的“不做项”；检查任务间依赖、共享接口调用方、回滚/部署说明。逐项记录“已覆盖 / 不适用+理由 / 待办”。
5. **置信度记录**：在任务文件末尾填写总任务数、完成数、不适用数、待办数、覆盖映射率、验证通过率、未核实来源项；只有待办为 0、每条原子需求都有映射、关键验收均有证据，且无未解释改动时，才可判断达到“至少 95% 把握无遗漏”。这是基于可见资料的工程判断，不是数学保证；资料缺失、无法运行验证或来源有歧义时必须说明未达到 95%，列出残余风险，不能强行宣布完成。
6. 最终答复报告任务文件路径、覆盖/验证统计、是否达到 95% 判断及依据、遗留项；不复制整份任务表。

## 8. 与标准工作流的衔接

1. 拆分在准入门禁（第 2 步）之后进行；先创建并落盘跟踪文件，子任务计划**先交用户确认**，确认后逐任务执行
2. 每个子任务独立走"最小实现（第 4 步）→ 真实验证（第 5 步）"，以任务单"范围/验收点"为边界，不越界实现后续子任务
3. 某任务执行中发现新联动点/遗漏 → 先评估对其他子任务的影响并更新跟踪文件，再继续
4. 全部子任务完成后，先执行第 7 节反向核对，再进入提交与交付（SKILL.md 第 6 步）；总结按子任务逐项汇报完成与验证情况
5. 跟踪文件写入 `.agents/out/coding/tasks/`，作为本地非 Git 托管产物；答复只摘要路径、进度与核对结论，不粘贴整份任务单

## 9. 失败模式守卫（历史实测）

- 方案里的字段后面被漏掉 / 字段名走样 → 覆盖映射表收口 + `git grep` 复查
- 只改主表、漏关联表 → 提取清单强制列关联表；映射表必须有"关联表→任务"行
- 只改 Entity 漏 Mapper XML 自定义查询 → 对齐硬性约束 16 逐 statement 判断
- 新表没有基础 CRUD 任务就先做复杂业务 → 原则 4 强制基础先行
- 复杂流转合并成一个巨型任务 → 原则 5 一动作一任务
- 拆分后凭方案文本直接写码、跳过现状扫描 → 第 2 节为拆分前置条件
- 口径不明硬拆 → 转"需确认项"，按准入门禁提问，不抢跑
- 只在聊天答复列了任务、未落盘跟踪 → 违反第 6 节，先补建完整任务文件再开始编码
- 全部任务打勾但未从原始文档反向核验 → 违反第 7 节；必须核对每条原子需求、附件和验收证据，不能凭主观判断宣称 95%
