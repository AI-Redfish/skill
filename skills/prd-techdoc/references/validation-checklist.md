# 校验清单

主 skill 在输出最终文档前，必须自检，并按 `agents/techdoc-structure-validator.md`、`agents/techdoc-content-checker.md` 的角色规则串行校验以下项目。问题按 P0/P1/P2 分级，行号/原文引用必须齐全。可机器化的检查由 `scripts/check-doc.py` 与 `scripts/check-mermaid.py` 执行（用法见 `verification-recipes.md`），并给出数字结果。

## 1. 结构校验（P0）

必须满足：
- 一级标题只有 6 个
- 一级标题顺序固定为（“接口清单”“增量字典”必须位于文档最后面）：
  1. `ER图`
  2. `增量SQL`
  3. `业务流程图`
  4. `数据流转图`
  5. `接口清单`
  6. `增量字典`

禁止出现：
- `方案概述`
- `设计目标与原则`
- `背景`
- `收益`
- `风险`
- `排期`
- 迁移/验收/事务等扩展一级章节
- 任何泛化总结章节

章节外只允许文末“待确认与需求冲突”段（二级标题或段落，不计入一级章节数）；文档内的冲突/差异/不确定点必须能在该段找到归集。

- 文档内不存在悬空章节引用（“见《某章节》”指向已被删除或改名的章节）；发现后修正引用文字或请示调用方，不擅自恢复被删内容
- 若调用方要求保留 Output Contract 之外的一级标题，必须先确认，再同步修改 Output Contract；不得默许出现计划外一级标题

## 2. 业务流程图校验（P0，涉及状态对象时）

- 有状态对象时必须给出实体状态机；每个状态机使用独立二级标题（`## 实体名称状态机`）和独立 `stateDiagram`，不得使用三级标题或统一放在二级容器下
- 每张状态机图后必须紧跟补充说明，至少覆盖状态归属/是否落库、关键触发与前置条件、终态或派生态、跨实体联动及异常限制
- 存在跨实体联动/触发时给出“实体间联动触发关系图”：按触发链路分段，每条链路独立一张 `flowchart`
- 不合并成一张总图；共享状态机（如多单据共用审批流程）说明“复用”，不重复画图
- 流程/链路各自分段，不合并成一张总图
- 图中出现但表中不落库的“过程叙述节点”（如仅由下游任务状态或时间字段推导的中间过程）必须在图后说明标注“不落库”并写清由哪个持久字段或任务状态推导展示
- 状态机图中出现的每个落库状态，都能在增量字典的对应字典项中找到同名取值；字典项也不得出现状态机中不存在的取值

## 2.1 状态字段一致性校验（P0）

- 同一业务事实只用一个状态字段：若两个状态字段取值一一对应（例如 A 的 X/Y/Z 恰好对应 B 的空/部分/全部），判为重复建模，必须合并
- 合并后“尚未发生”统一用 NULL 表达，页面显示 `-`，该展示值不落库
- 新增状态（尤其终态）必须闭环：写明触发方与动作、写入的时间字段、是否不可逆、进入后必须拒绝的接口与错误码、历史数据是否回填
- 状态字段的中文文案、取值字符串与 SQL 注释、字典项、状态机节点、接口备注完全一致

## 2.2 口径变更六处同步（P0）

当需求方给出与 PRD/原型不同的口径（例如某状态不应存在、新增终态、条件变更后历史数据的可见性变化），逐项确认已同步：

1. ER 字段（新增/删除/改名）
2. SQL 字段注释与取值枚举
3. 状态机节点与图后说明
4. 数据流转图节点
5. 接口备注、前置校验与错误码
6. 增量字典的字段行与字典项

并确认冲突/采用口径段记录了该裁决、采用口径与依据。任一处缺失即判 P0，回到文档补齐后重跑图形与字典检查。

外部域条件驱动的可见性额外校验（仅当 PRD/原型明确规定时适用，不套用无关需求）：
- 本模块扩展数据是否按口径保留历史，是否明确禁止软删或级联删除
- 列表是否按外部域实时条件过滤；历史数据与统计是否受该条件影响，口径是否写清
- 条件移除或变更后，是否明确新单据、进行中流程和重复操作的处理方式
- 条件重复出现时是否复用原有扩展记录，是否明确不重建

## 2.3 图形安全与渲染校验（P0）

- 所有 Mermaid 图必须通过 `scripts/check-mermaid.py` 校验（配置 `MMDC_PATH` 时真实渲染，否则内置结构化 lint），失败数为 0；只做肉眼检查不算通过
- 节点标签中的 ASCII 括号、竖线、冒号等易错字符必须改为全角标点或整体加引号
- lint 模式通过时在答复中说明“未做真实渲染校验”；仅当脚本完全不可运行时才降级为人工逐图检查并在答复中说明

## 3. 接口风格、安全与可测试性校验（P0/P1）

接口清单应尽量符合现有仓库风格：
- 每个接口单独成段，不输出前端函数名；至少写清 URL、Method、Controller、请求参数、响应参数
- 请求/响应使用表格，至少包含：字段名、类型、必填、字段含义、字典编码；同构接口只列差异
- `list/add/update/delete` 多为 `POST`；`view`、轻量查询可能为 `GET`；复杂组合入参可说明 `@MyRequestBody`
- 外部接口明确权限码或登录要求；关键数据明确租户/院区/组织范围和服务端身份来源
- 不信任客户端 tenantId/userId/campusId/动态排序字段；模糊搜索、批量入参有转义或上限
- 状态写接口明确前置状态、目标状态、错误码、事务、幂等/重复提交和并发处理
- 列表必须分页并限制 pageSize；批量、导入导出、复杂统计、外部调用有数量上限、异步或超时/失败策略
- 每个关键接口至少给出 1 条正向和 1 条最高风险负例依据；简单只读接口可合并说明

## 4. SQL 校验（P0/P1）

- 只给增量 SQL，不给全量建库方案
- 增量SQL章节只允许输出 MySQL 语法，不生成、不比较、不说明其他数据库方言
- 增量SQL章节先输出 SQL 代码；代码块后必须紧跟二级段落 `流程引擎实体与状态机实现边界`，除此之外不要附加说明文字，该段不得成为新的一级标题
- `流程引擎实体与状态机实现边界` 必须覆盖全部有状态实体，并逐项写明：实体/对象、实现方式、流程引擎职责、状态机/联动职责、关键字段/约束
- 对明确存在审批生命周期的单据，检查是否采用“流程引擎 + 业务状态机”并分离流程状态与业务状态；检查审批开启时创建流程实例、审批关闭时不创建实例并走免审批直通、免审批内部流程状态与页面 `-` 展示（`-` 不落库）口径、流程回调通过后才触发后续业务状态
- 普通业务状态（草稿、执行、完成、关闭、交接、核算等）不得仅因存在 `status` 字段而接流程引擎；外部单据应标注复用外部领域实现
- **新增/变更表只保留主键（含复合主键），不得出现外键、UNIQUE 唯一键或其他索引**；业务唯一性/幂等/防并发由服务层与事务锁保证
- **每张新增/变更表必须有表级 `COMMENT`（说明表用途）**；**每个业务字段必须有列级 `COMMENT`（说明作用/取值）**；主键与审计字段（`create_user_id`/`create_time`/`update_user_id`/`update_time`）不要求列注释
- 若文档确需数据库级兜底约束，只能在文末“待确认与需求冲突”段以调用方确认项形式说明，不能写入建表 SQL
- 存量库变更（ALTER/初始化/迁移要点）在 SQL 注释中标注“存量迁移，非新库脚本”，说明可重复执行、历史回填和回滚注意项；不得建议修改已发布历史 Flyway
- 过滤、排序、关联、状态、租户字段存在索引需求时，受当前 DDL 约束不直接建索引，需以“查询场景 + 影响 + 所需确认”归入待确认项

## 5. ER / SQL / API 一致性校验（P0）

- ER图章节只保留 Mermaid 图，不附加文字说明
- ER图必须体现实体名称和字段，不能只有关系线；只标注主键 `PK`（含复合主键）与“复用/外部”实体，不标注业务唯一键
- 每个新增实体都应在 ER 图与增量 SQL 中出现
- 复用已有实体/表不得画成新实体
- 每个关键业务动作都应在接口清单或流程图中找到映射；无法映射或冲突的内容进入文末“待确认与需求冲突”段
- 每个新增字典字段都要在接口或实体中有落点
- 数据流转图必须按链路分段展示，串起“页面动作 -> 前端 API -> Controller -> Domain Service -> DB/字典/记录表”，并标明模块归属、跨服务/外部依赖、事务或异步边界（适用时）
- 方案不得新增 `common -> application`、`service -> service`、Bean 双向依赖、自注入或以 `@Lazy` 作为循环依赖解决方案

## 6. 增量字典校验（P0/P1）

- 增量字典只列实体字段实际使用的字典，不得混入术语总览、页面位置、DictMap、派生展示状态、非字典布尔项或算法说明
- 必须包含“实体字段字典使用清单”，列固定为：实体、字段、字典编码、字典名称、字典类型；逐字段写明所用字典编码
- 必须包含“字典枚举项”，且每个字典编码有且只有一个三级标题（格式 `### 字典编码（字典名称）`）和一张字典项表，列固定为：字典项编码、字典项名称、说明
- 常量字典和自定义字典必须逐项列全字典项；同一编码被多个字段复用时只建一张表
- 使用清单中的编码与“字典枚举项”的三级标题必须一一对应：不得有缺失表格的编码，也不得有未被任何字段引用的孤儿字典表
- 字典类型只允许常量字典、全局字典、自定义字典；单据状态、流程状态及稳定任务/业务状态原则上是常量字典
- 跨域字典必须复用平台既有编码（如 `assetUseCategory`、`EnabledStatusDict`），不得另造同义编码；本模块新增编码沿用“模块前缀 + 业务名”风格
- 引用 UPMS 组织、人员、班组等外部主数据、仅经 `xxxDictMap` 回填名称的字段不得列为字典编码
- 平台公共主数据标记为全局字典；动态字典项写“平台动态项，由来源域维护”
- 只有字典中心新增并可配置维护的业务项标记为自定义字典；编码未确认时写“编码待分配”，不得臆造
- 同一编码的字典项编码、名称与 SQL 注释、接口及状态机用词一致
- 接口中的 `xxxDictMap` 命名另按前端接口风格校验，不要求写入增量字典章节

## 7. 内容口径校验（Mode C / 质量门，交 `techdoc-content-checker`）

- 从当前 PRD/原型动态提炼事实域，不套用其他业务的计费、台账、配送等固定规则
- 范围/动作、实体/字段、状态/字典、规则/算法、权限/数据范围、事务/幂等、复用/外部边界、性能、验收等适用事实与 PRD 一致（行号证据）
- 无 PRD 依据的孤儿能力删除/挂起或明确待确认；旧口径只作为“不采用/待清理”出现
- 每条结论带 PRD 行号与（如适用）原型行号证据

## 8. 信息不足处理

如果关键信息不足：
- 核心对象/状态、模块与复用边界、主键/历史数据、权限/数据范围、跨服务边界或 P0 验收路径不清时，判 `BLOCK`，不生成确定性接口、ER 和 SQL
- 仅非核心信息不清时判 `CONDITIONAL`，不脑补真实表名、DTO、权限码、字典编码或模块路径
- 待确认项统一归集文末，写清问题、影响和责任方/所需输入

## 9. 简洁性校验（P1/P2）

- 不复述背景、价值、PRD 原文、通用技术常识或章节总结
- 普通说明最多 3 句，超出时拆为短条目；结构化内容优先表格
- 公共参数/响应/校验和同构接口只定义一次，后续只列差异
- 图后只保留状态归属、触发条件、数据变化、异常限制和跨实体联动
- 待确认项合并同类内容，不在多章重复解释

## 10. 偏离声明复核（P1/P2）

- 文档以约定标记（如 `> 偏离说明：`、SQL 注释）声明的通用约定例外，作“已裁决偏离”复核，不重复判 FAIL
- 未声明的偏离报 P1（补声明或修正内容）
