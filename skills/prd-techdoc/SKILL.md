# PRD 转后端开发文档

## Overview

这个 skill 用于把 PRD（Markdown）和产品原型（HTML）转换成**贴近现有代码风格**的后端开发文档。

它不是泛化“方案文档生成器”。它的目标是产出可直接给后端开发使用的关键内容：`ER图`、`增量SQL`、`接口清单`、`业务流程图`、`数据流转图`、`增量字典`。

## 双闭环流程（最高优先级，优先于其他默认行为）

完成用户任务时必须遵循以下双闭环；当本规则与基础行为习惯冲突时，以本规则为准。

### 第一闭环：理解闭环
1. 回答前先提问，**每次只问一个问题**，根据回答继续追问。缺 PRD/原型时“提示用户提供”、
   Design Readiness Gate 的追问都属于理解闭环的问题，逐个提出
2. 提问围绕：真实目标、背景、使用场景、输出对象、关键约束、优先级、
   成功标准、禁止事项、已有信息、可接受偏差（含代码风格参考路径、数据库环境）
3. 对“用户真正想要什么”有 95% 信心才停止提问；未达 95% 只提问澄清，
   不给最终方案（不脑补生成文档）

### 第二闭环：输出审查闭环
1. 形成答案后不直接输出，先自查：是否真正解决目标？是否遗漏关键约束（硬约束/风格）？
   是否存在事实错误、逻辑漏洞、歧义、不可执行之处？与 PRD/原型的口径是否一致？
2. 发现问题→自行修正→再次审查，重复“审查—修正—再审查”，
   直到对输出结果至少有 95% 的准确性信心（用 scripts/check-doc.py 等本地脚本辅助校验）

### 最终输出要求
1. 先一句话复述用户真实需求
2. 再给出最终方案：明确、可执行、可直接使用（六章节文档 + 待确认与需求冲突段）
3. 说明关键假设、剩余不确定性（未连接真实库核对等降级项），
   以及为什么已达到 95% 信心；不确定处明确标注，不假装确定

## When to Use

在以下场景必须使用本 skill：
- 用户要求“把 PRD 转成后端开发文档/后端技术方案”
- 用户要求“根据原型和 PRD 产出接口、ER 图、SQL、字典、流程图”
- 用户要求“梳理后端 API、表结构、数据流转、业务流程”
- 用户明确要求输出必须参考现有后端、前端代码风格
- 用户要求“把已有技术文档整合成一份 / 完善修复既有技术文档”时，按下面的工作模式处理
- 用户要求“根据 PRD/原型核对已有技术文档”时，按事实复核模式处理

以下情况不要直接套用本 skill：
- 用户只想要产品总结、方案概述、里程碑、排期
- 用户只要前端页面说明，不需要后端接口/数据结构
- 用户要直接生成完整业务代码，而不是文档

## When NOT to Use（不适用场景）

以下情况不要使用本 skill，避免误触发（与上表互补，含跨 skill 分流）：

- 用户只想要产品总结、方案概述、里程碑、排期 → 直接回答，不生成本 skill 的六章节文档
- 用户只要前端页面说明，不需要后端接口/数据结构 → 直接回答或用前端类 skill
- 用户要直接生成完整业务代码，而不是文档 → 按用户要求写代码
- 用户要评审 PRD 找缺失/歧义/风险、输出评审报告 → 用 `prd-review`
- 用户给 bug 单号要求定位/修复代码 → 用 `zentao-bugfix`

## Work Modes

调用前先判断输入形态并选择工作模式：

- **Mode A：PRD/原型 → 新文档**（默认）。按“Execution Flow”从零抽取并生成，输出遵循 Output Contract。
- **Mode B：既有文档整合/改进**（例如把多份既有技术文档/设计说明合并成一份，或按 PRD/原型完善既有文档）。必须：
  1. 先做“差异与口径映射清单”：列出每份来源文档的关键结论、章节、与 PRD/原型的冲突点、重复内容、以及整合后应落在哪个输出章节；
  2. 再做内容合并与去重，**不得简单拼接、不得丢弃来源中的既有设计结论**（如关键业务口径、互斥或边界规则、算法常量、事务/并发约束、迁移要点、验收要点，若 6 章中无处表达，统一归入“待确认与需求冲突”段或相应章节内说明）；
  3. 最终输出仍遵循 Output Contract（6 个一级章节 + 状态机/实体联动图 + 待确认与需求冲突段），不新增一级章节。
- **Mode C：事实复核**（对照 PRD/原型校验一份已有技术文档）。跳过生成步骤，按“Content-Check”核对文档口径与 PRD/原型行号证据，输出修订清单。

## Dependency Checks

本 skill 无任何必须安装的运行时依赖：不调用 MCP 服务、不依赖宿主 `Agent`/`Task` 子代理工具、不依赖本机预装 mmdc/Chrome。原先这些能力全部改由 `scripts/` 内置本地脚本实现；任何脚本或环境缺失都不阻断执行，只降级并在结果中标注。

### 1. 输入文档（唯一必需依赖）

- PRD（`*.md`）与原型（`*.html`）**至少提供其一**：只有 PRD、只有原型均可执行，两者都有最好（PRD 是业务权威，原型是 UI/交互事实）
- Mode B 需至少一份既有技术文档；Mode C 需既有技术文档 + PRD 或原型至少其一
- 全部缺失时提示用户提供，不脑补生成

### 2. 环境信息（.agents/.env）

本地脚本所需的可选环境信息保存在 **skill 运行时工作目录**的 `.agents/.env`（UTF-8 文本，`键=值`，一行一项，`#` 注释）：

| 键 | 用途 | 未配置时行为 |
| --- | --- | --- |
| `DB_HOST` / `DB_PORT` / `DB_USER` / `DB_PASSWORD` / `DB_NAME` | `scripts/db-schema-check.py` 连接真实 MySQL 核对表结构 | 跳过真实库核对；SQL 照常输出，并在“待确认与需求冲突”段注明“未连接真实库核对 schema” |
| `MMDC_PATH` / `CHROME_PATH` | `scripts/check-mermaid.py` 优先做真实渲染 | 自动降级为脚本内置结构化 lint（不真实渲染），答复中说明“未做真实渲染校验” |
| `BACKEND_PATH` / `FRONTEND_PATH` | 对齐真实前后端项目风格 | 输出建议稿，风格遵循内置 references，待确认段标注 |

规则：
1. 脚本报告缺少环境信息（退出码 2 或 `MISSING_ENV` 输出）时，由主调用方提示用户输入，再由主调用方写入/更新 `.agents/.env` 后重跑脚本；用户拒绝或跳过不阻塞，按上表降级。
2. 脚本只读取 `.agents/.env`，一律不写入；所有写入由主调用方完成。
3. `.agents/.env` 可能包含数据库口令，提醒调用方将其加入版本控制忽略清单。
4. 键清单与示例见 `scripts/env.example`。

### 3. 本地脚本（替代 MCP / 通用 Agent / mmdc，Python + uv）

所有脚本位于本 skill 的 `scripts/`，Python 3.9+ 编写（纯标准库，跨平台）。**依赖统一用 uv 管理**：`check-doc.py` 与 `check-mermaid.py` 零第三方依赖；`db-schema-check.py` 通过 PEP 723 内联元数据声明 `pymysql`，`uv run` 自动创建隔离环境并安装，不污染全局。

运行方式（优先 uv，无 uv 时降级直跑）：

```bash
uv run scripts/check-doc.py --md <doc.md>            # 推荐：uv 自动隔离
python scripts/check-doc.py --md <doc.md>            # 等效：纯标准库直接跑
uv run scripts/db-schema-check.py --tables "t_a,t_b"  # uv 自动隔离安装 pymysql
python scripts/db-schema-check.py                      # 无 uv/无 pymysql 时降级 mysql CLI
```

脚本只读不写被检文档，以非零退出码表示发现问题（`1` = 检查未通过；`2` = 输入或环境缺失，属降级场景）：

| 脚本 | 替代项 | 依赖 |
| --- | --- | --- |
| `scripts/check-mermaid.py` | mmdc + Chrome 渲染校验 | 无（渲染模式下调用 mmdc 为可选增强） |
| `scripts/check-doc.py` | 结构自检（原 verification-recipes 机器化步骤） | 无 |
| `scripts/db-schema-check.py` | `mcp:@bytebase/dbhub` | pymysql（uv 管理，缺失时降级 mysql CLI） |
| （内置替代） | `mcp:@upstash/context7-mcp` | 由内置 `references/*` 与真实项目路径替代 |

能力说明：
- `check-mermaid.py`：提取全部 Mermaid 块并校验；配置 `MMDC_PATH` 时逐块真实渲染（全部渲染失败视为渲染环境问题，自动回退 lint），否则内置结构化 lint（图类型、空块、未闭合、引号不配对、未加引号的 ASCII 括号/竖线/冒号、erDiagram/stateDiagram/sequenceDiagram 常见语法错误）；输出 `mode` 与 `mermaid_blocks=N failures=N`
- `check-doc.py`：一级标题数量/顺序/禁用章节、状态机二级标题与图后说明、增量字典编码交叉校验、重复状态字段扫描、悬空章节引用、非 MySQL 方言扫描、ER 实体与 SQL 表名对应；输出各项数字结果
- `db-schema-check.py`：读 `.agents/.env` 的 `DB_*`，优先 pymysql、降级 mysql 客户端执行 `SHOW TABLES` / `SHOW CREATE TABLE` 核对真实表结构；口令经环境变量传递不上命令行
- `context7` 替代：内置 references + 真实项目路径；最终文档标注“框架/库文档以实施时官网为准”

脚本运行失败或运行环境（Python / uv / mysql 客户端）不可用时，降级为人工检查并在答复与“待确认与需求冲突”段说明，不视为 skill 失败。

本 skill 不检查、不依赖宿主是否提供 `Agent`/`agent`/`Task` 等子代理工具，也不依赖 `.claude/agents` 中预装的自定义 subAgent。以下角色提示词随 skill 存放在 `agents/`，安装即携带：
- `agents/prd-entity-flow-extractor.md`
- `agents/backend-contract-designer.md`
- `agents/schema-sql-dict-designer.md`
- `agents/techdoc-structure-validator.md`
- `agents/techdoc-content-checker.md`（Mode C 或 Mode A 质量门使用）

执行规则：
1. 五个角色一律由主调用方在当前上下文**串行扮演**：进入角色前先完整读取对应 `agents/*.md` 正文，严格按角色规则处理本轮输入。
2. 扮演某角色时携带本轮具体输入（文件路径、前序角色的结构化结果、真实项目路径、期望输出），不得凭记忆省略角色规则。
3. 角色只产出分析结果或草稿；最终文件读写、汇总和修订由主调用方负责。
4. 机器可判定的检查（结构、字典、渲染、方言、库表核对）交给本地脚本执行，角色只负责需要判断力的部分。
5. 某个内置角色文件损坏或缺失：由主调用方按本 `SKILL.md` 的 Output Contract、Style Constraints 和 references 自行补位。

## Required Inputs

优先读取以下输入：
- PRD `*.md` 与原型 `*.html`：**至少提供其一**，都有最好（PRD 是业务权威，原型是 UI/交互事实）
  - 只有原型时：以原型为业务事实源，页面动作与交互口径从原型提取；PRD 级业务规则缺口进入“待确认与需求冲突”
  - 只有 PRD 时：接口出入参、页面动作等 UI 事实缺失处标“待确认”，不臆造交互细节
- 既有技术文档（Mode B：必填；Mode C：必填，且需 PRD 或原型至少其一作为核对基准）
- 后端/前端项目路径：可选；可由用户直接给出，也可从 `.agents/.env` 的 `BACKEND_PATH` / `FRONTEND_PATH` 读取

输入处理要求：
1. PRD 与原型都缺失（Mode A）、或既有文档缺失（Mode B/C）时，先提示用户提供，不要直接生成。
2. 不要只因为工作区里“可能存在”同类文件就自动替用户拍板；如果无法明确判断哪份是目标 PRD、哪份是目标原型，要先向用户确认。
3. 前端/后端项目路径为可选项：
   - 未提供：输出建议稿，风格遵循内置 references，并在“待确认与需求冲突”段标注“路径/模块归属待接入真实项目后确认”。
   - 已提供：优先对齐真实项目风格（references 中的路径仅是风格锚点示例，不视为必须存在的代码位置）。
4. 缺少关键输入时，先按“设计准入分级”判断能否继续，不得把阻断项降格为普通“待确认”。

## Design Readiness Gate

生成确定性接口、ER 或 SQL 前，先在内部完成准入判断；该判断用于控制生成流程，默认不写入最终文档，不增加章节。

- `PASS`：核心业务边界和实现依据完整，可生成确定性设计。
- `CONDITIONAL`：仅非核心细节未确认，可继续生成；相关位置标“待确认”并汇入文末。
- `BLOCK`：暂停确定性设计，只输出阻断项和所需补充材料。

以下任一项不清楚时判为 `BLOCK`：
- 核心业务对象、写入事实或状态转换存在无法裁决的冲突
- 新增还是复用已有模块、实体或表无法判断，且会改变方案主体
- 主键、数据归属、历史保留或存量迁移规则不清
- 对外写接口的权限、租户/院区/组织数据范围无法落地
- 跨服务、外部系统、消息或流程引擎边界无法确定
- 无法构造 P0 主链路和至少一条关键失败路径

以下通常可判为 `CONDITIONAL`：非核心文案、低优先级排序、未分配的自定义字典编码、建议稿类名/包路径、暂不可用但已有明确契约的联调环境。

## Output Contract

最终文档只允许保留以下 6 个一级章节，且顺序固定（**“接口清单”与“增量字典”必须放在文档最后面**）：
1. `ER图`
2. `增量SQL`
3. `业务流程图`
4. `数据流转图`
5. `接口清单`
6. `增量字典`

段落顺序约束（按“技术内容先行、接口与字典收尾”固定，正文各 H2/H3 沿用当前技术文档的既有段落顺序，不要重新排版）：
- 前置：`ER图` → `增量SQL`
- `增量SQL` 内部：先给 MySQL 增量 SQL 代码块，代码块后固定新增二级段落 `流程引擎实体与状态机实现边界`，然后才进入 `业务流程图`；该段不新增一级标题
- 中置：`业务流程图` → `数据流转图`
- 收尾：`接口清单` → `增量字典`（在全文最后；`增量字典` 内部按其既有小节顺序排列，“待确认与需求冲突”作为其末尾段或文末追加）

严禁出现以下一级章节：
- `方案概述`
- `设计目标与原则`
- `背景`
- `收益`
- `风险`
- `排期`
- `迁移方案`、`验收用例`、`事务与并发` 等任何泛化/扩展型一级章节
- 任何泛化总结型章节

在以上 6 个一级章节之外，只允许在**文档末尾**附一段“待确认与需求冲突”（可用二级标题或段落，不计入一级章节数），集中列明：需求冲突与采用口径、PRD/原型/既有文档之间的差异、无法确定而需产品/前端/后端补充的点、真实库与项目路径未核对项。各章节内部如需记录不确定内容，用“待确认”标注并汇入该段。

不得为权限、事务、性能、测试、审计、迁移或模块边界新增一级章节，按以下位置就近表达：
- 权限码、登录态、租户/院区/组织数据范围、入参校验、错误码、幂等和并发前提：放在对应接口备注
- 模块归属、跨服务方向、外部依赖、消息/缓存/异步链路：放在数据流转图及图后短条目
- 事务边界、状态前提、失败回滚和补偿：放在业务流程图图后短条目或关键写接口备注
- 存量迁移、历史回填和回滚注意项：写成增量 SQL 内的简短注释；无法确定的内容汇入文末
- 性能容量：仅在受影响接口备注中写分页上限、批量上限、索引待核、异步或超时等可执行约束，不输出泛化 SLO 大段文字
- 测试依据：仅在关键接口备注中列“正向 / 关键负例 / 权限或状态校验”短条目，不另建测试章节

`业务流程图` 章节在原有“按流程分段”基础上，必须覆盖用户可能要求的两种图，且**各自独立成图、不合并为一张总图**：
- 若需求中存在有状态的对象（单据/任务/记录/规则等），给出实体状态机：**每一个状态机必须使用独立二级标题（`## 实体名称状态机`）和独立 Mermaid `stateDiagram`**，不得用三级标题，也不得在“各实体状态机流转图”二级容器下统一降为三级标题；节点命名与 PRD/现有工程状态一致。
- **每一张状态机图后必须紧跟补充说明**，至少说明状态归属/是否落库、关键触发动作与前置条件、终态或派生态、跨实体联动及异常限制；不得只有图没有文字。
- 若实体之间存在联动/触发（如 主单据确认→明细落库→下游对象生成），给出“**实体间联动触发关系图**”：按触发链路分段，每条链路一张 Mermaid `flowchart`。
- 发现可复用的共享状态机（如多个单据共用审批流程状态机）时单独说明“复用”而不是为每个实体重复画同图。

文档模板见 `templates/techdoc-template.md`。

## Style Constraints

生成时必须对齐现有代码风格，而不是用通用 REST/DDD 模板：
- 后端 controller / service / Flyway / 字典命名风格：见 `references/backend-style.md`
- 前端 API 命名、路径组织、`xxxDictMap` 风格：见 `references/frontend-api-style.md`
- 最终结构校验项：见 `references/validation-checklist.md`
- 交付前机器化自检步骤与命令：见 `references/verification-recipes.md`

关键约束：
- ER图只保留 Mermaid `erDiagram`，不要附加文字说明
- ER图必须包含实体名称和字段，不允许只画实体关系线；只标注主键 `PK`（含复合主键）与“复用外部表”，不标注业务唯一键（唯一性由服务层保证）
- 增量SQL只提供 MySQL 语法；不生成、不讨论、不预留其他数据库方言
- 增量SQL章节先放 SQL 代码；SQL 代码块后唯一允许的说明性内容是固定二级段落 `流程引擎实体与状态机实现边界`，不得把该段写入 SQL 注释、业务流程章节或新增一级标题
- `流程引擎实体与状态机实现边界` 必须逐实体分类为：流程引擎、业务状态机、流程引擎+业务状态机、联动投影/外部复用；至少列明实体、实现方式、流程引擎职责、状态机/联动职责、关键字段或约束
- 只有 PRD/原型明确存在审批、会签、撤回、驳回、终止等流程生命周期的实体才接流程引擎；不能因实体存在 `status` 字段就默认创建流程实例
- 混合实现必须写清流程引擎与领域状态机的交接点：审批开启时何时创建流程实例、流程回调如何同步流程状态并触发后续业务状态；审批关闭时不得创建流程实例，应按免审批路径直通，并明确内部流程状态落值与页面 `-` 展示（`-` 不落库）口径
- 草稿、执行中、完成、关闭、交接、核算等普通业务状态原则上由业务状态机/领域服务承载；如需求明确要求流程引擎，必须给出证据并在边界段说明
- **建表 SQL 每张表只保留主键（含复合主键），不建立外键、UNIQUE 唯一键及其他索引**；业务唯一性/幂等/防并发由服务层与事务锁保证，需要数据库级兜底约束时写入“待确认与需求冲突”段由调用方决策，不得私自在 SQL 中添加
- **每张表必须带表级 `COMMENT`（用途说明）**；**每个业务字段必须带列级 `COMMENT`（字段作用/取值含义）**；主键与审计字段（`create_user_id`/`create_time`/`update_user_id`/`update_time`）不写列注释
- 接口清单优先沿用现有接口语义，例如 `list` / `add` / `update` / `delete` / `view`
- 若需求涉及的模块、实体或能力在项目中已存在，优先复用现有模块、实体、表结构、接口与字典，不要为了需求重新创建新实体
- 接口清单不输出“前端函数名”
- 每个关键接口独立成段；请求参数、响应参数用表格展示（字段名、类型、字段含义、字典编码）。同构接口（如仅 ID 入参的 detail）可用公共参数表 + “其余同 X”注明，避免重复整表
- 复杂组合入参要按现有后端习惯描述 `@MyRequestBody`
- 接口请求/响应中的字典映射字段仍采用 `field` + `fieldDictMap` 风格，例如 `status`、`statusDictMap`；同名不同域字段须消歧。此命名规则不要求写入“增量字典”章节
- `增量字典` 只说明实体字段实际使用的字典，不写术语总览、页面位置、DictMap、派生展示状态、非字典布尔项或算法说明
- `增量字典` 先用“实体字段字典使用清单”表列明 `实体 | 字段 | 字典编码 | 字典名称 | 字典类型`，逐字段说明该字段使用哪个字典编码；引用 UPMS 组织、人员、班组等外部主数据、仅经 `xxxDictMap` 回填名称的字段不属于字典编码，不应列入该表
- `增量字典` 再用“字典枚举项”段列明每个字典编码下的字典项：**每个字典编码一个三级标题和一个独立表格**，标题格式为 `### 字典编码（字典名称）`，表格列固定为 `字典项编码 | 字典项名称 | 说明`
- 同一字典编码被多个字段复用时只建一张表，由使用清单中的多行指向同一编码；不得为同一编码重复建表或改写成多个名称
- 字典编码命名沿用现有工程风格（模块前缀 + 业务名，如 `PurchaseBudgetSubject`、`assetUseCategory`、`EnabledStatusDict`），跨域字典直接复用平台既有编码，不得为本模块另造同义编码
- 字典类型只允许：`常量字典`、`全局字典`、`自定义字典`。单据状态、流程状态及稳定的任务/业务状态原则上使用常量字典；平台公共主数据使用全局字典；只有需要字典中心新增并可配置维护的业务项使用自定义字典
- 全局动态字典的字典项写“平台动态项”并注明由来源域维护；自定义字典编码未确认时写“编码待分配”，不得臆造编码
- 业务流程图不要合并成一张总图；不同流程按段落分开，各自给 Mermaid 图；每个状态机使用二级标题、独立成图且图后有关键说明，联动触发图按要求独立成图
- 数据流转图不要合并成一张总图；不同数据链路按段落分开，各自给 Mermaid 图
- 图统一用 Mermaid；节点标签出现 ASCII 括号、竖线、冒号等易错字符时必须改为全角标点或整体加引号，并在交付前用 `scripts/check-mermaid.py` 校验（真实渲染或结构化 lint），不能只靠肉眼检查

### Concise Writing Rules

- 结论先行，优先使用表格、短列表和 Mermaid；除必要口径说明外，不写连续大段文字
- 每个普通说明段控制在 3 句以内；超过 3 句时拆为条目，每条只表达一个约束或结论
- 不重复 PRD 原文，不写背景复述、价值说明、通用技术常识、实现口号或章节总结
- 接口间公共参数、公共响应和公共校验只定义一次，后续接口引用差异，不重复整表
- 图后说明只保留状态归属、触发条件、数据变化、异常限制和跨实体联动；无实际内容的维度不输出占位话术
- 待确认项使用 `问题 | 影响 | 责任方/所需输入` 的短表格或短条目，合并同类项，不在多个章节重复解释
- 真实项目已有能力只写“复用对象 + 差异”，不抄录无变化的存量结构

### Implementation-Ready Checks

不新增章节，但生成内容必须覆盖以下必要设计信息：
- 模块边界：优先复用现有业务域；禁止建议 `common -> application`、`service -> service`、Bean 双向依赖、自注入或用 `@Lazy` 掩盖环
- 接口安全：外部接口明确权限或登录要求；写接口明确租户/院区/组织数据范围、服务端身份来源和越权拒绝
- 输入安全：必填、长度、枚举、批量上限、模糊搜索转义和动态排序白名单按风险写入接口备注
- 事务一致性：多实体写入明确事务边界、失败回滚、幂等/重复提交和并发前提
- 性能：列表必须分页并限制 pageSize；禁止无界查询、循环查库和同步大导出；外部慢调用写明超时/异步/补偿
- 可测试性：关键接口至少给出一条正向依据和一条关键负例；状态写接口还要覆盖非法状态、重复提交或权限隔离

## Hard Invariants（口径一致性硬约束）

以下不变式由实际返工教训沉淀，属 P0 级要求，生成与修订都必须满足：

1. **单一状态字段**：同一个业务事实只用一个状态字段表达。若两个状态字段取值一一对应（一个字段的多个取值恰好映射另一个字段的空值/部分/全部），必须合并为一个字段，用空值（页面显示 `-`）表达“尚未发生”，不得保留双写。发现同义双字段时先合并再落文档，并在冲突段记录裁决依据。
2. **状态机图与落库状态一致**：`stateDiagram` 中出现但表中不落库的过程节点，必须在图后说明中标注“过程叙述节点，不落库”，并说明由哪个持久字段或任务状态推导展示。
3. **新增终态必须闭环**：新增一个状态（尤其终态）时，必须同时给出触发方与触发动作、写入的时间字段、是否不可逆、进入后哪些接口必须拒绝（返回什么错误码）、历史数据是否回填。
4. **口径变更六处同步**：当需求方给出与 PRD/原型不同的口径（例如某状态不应存在、新增终态、条件变更后历史数据的可见性变化），该口径必须同步落到六处：ER 字段、SQL 字段注释与取值、状态机节点与图后说明、数据流转图、接口备注与前置校验、增量字典；并逐条写入冲突/采用口径段并注明依据。任一处未同步视为未完成。
5. **外部域条件驱动的可见性**：仅当 PRD/原型明确规定对象可见性由外部域标签、分类或资格条件控制时启用。必须写清实时列表、历史数据、进行中流程和条件移除后的处理口径；不得把示例业务规则套用到无关需求。
6. **字典与状态用语一致**：同一状态/枚举的取值字符串与中文名称必须与 SQL 注释、字典项、状态机节点、接口备注完全一致，不得在不同章节用同义改写。
7. **协作修订守则**：文档可能被用户在会话外直接修改。每次编辑前重新读取目标段落，不整篇覆盖；发现结构偏差（如引用了已被删除的章节名、出现未被契约允许的一级标题）时只报告并请示，不擅自恢复或删除用户内容。

## Execution Flow

按下面顺序工作，不要跳步：

1. 先做依赖检查与降级（见 Dependency Checks）：确认 PRD/原型至少其一（Mode B 确认既有文档）、读取或提示补全 `.agents/.env`、确认本地脚本可运行；并确认输入形态选择 Mode A/B/C。
2. 校验输入和路径，执行 Design Readiness Gate；`BLOCK` 时停止确定性设计，只列阻断项与所需输入。
3. 读取 PRD/原型/既有文档，识别模块、页面动作、字段、权限、数据范围、约束、异常和验收点（PRD 与原型至少其一，按 Required Inputs 的缺失侧降级规则处理）。巨型 HTML 用关键词定位后按行区读取并附行号；旧口径只进入差异项。
4. 读取真实前后端项目中的相似实现（路径来自用户指定或 `.agents/.env`），确认模块边界、复用对象、Controller/Service/Mapper 分层和跨服务依赖；未提供路径时使用内置参考并标建议稿。
5. 生成字典草案：只识别实体字段实际使用的常量/全局/自定义字典及其枚举，不收录展示派生态。
6. 完整读取 `agents/prd-entity-flow-extractor.md` 并按该角色规则执行（本地串行，见 Role Execution），提取实体、动作、流程、数据流、口径变更、权限/数据范围、异常、验收和待确认项。
7. 完整读取 `agents/backend-contract-designer.md` 并按该角色规则执行，基于步骤 6 和真实项目风格产出简洁接口清单；关键接口补齐权限、校验、状态、事务、幂等、性能上限和最小测试依据。
8. 完整读取 `agents/schema-sql-dict-designer.md` 并按该角色规则执行，产出 ER、仅 MySQL 的增量 SQL、字典和流程引擎边界分类；同时核对存量迁移、历史回填和查询字段的索引需求是否需要进入待确认项；若 `.agents/.env` 已配置 `DB_*`，运行 `scripts/db-schema-check.py` 核对涉及表的真实结构。
9. 按模板汇总；不新增一级章节，按 Output Contract 的信息落位规则写入现有章节。Mode B 先合并去重既有结论。全文按 Concise Writing Rules 压缩重复和泛化说明。
10. 完整读取 `agents/techdoc-structure-validator.md` 并按该角色规则检查结构、简洁性、架构、安全、性能与一致性（机器可判定的部分直接采用脚本结果）；Mode A/C 再完整读取 `agents/techdoc-content-checker.md` 按 PRD/原型事实域抽检。修正后复检。
11. 按 `references/verification-recipes.md` 运行本地脚本做机器化自检：`scripts/check-doc.py`（状态机标题/图后说明、字典映射、重复状态字段、一级标题、悬空引用、非 MySQL 方言、ER/SQL 对应）与 `scripts/check-mermaid.py`（Mermaid 全量校验）；需要时按 DB 核对结果补跑 `scripts/db-schema-check.py`。优先 `uv run` 隔离运行，无 uv 时纯标准库脚本可直接 `python` 运行。最终答复给出数字结果。
12. 修订既有文档时遵守 Hard Invariants 第 7 条：编辑前重读目标段落，不整篇覆盖；口径变化同步六处后再收尾。

## Agent Dispatch（本地串行 Role Execution）

所有路径均相对于本 `SKILL.md` 所在目录解析。角色文件是 prompt 资源，不是需要另外安装的 Claude Code custom agent；本 skill 不使用任何子代理工具调度它们，一律由主调用方在当前上下文串行扮演。

进入角色前先完整读取对应 `agents/*.md` 正文，并按下述结构组织本轮工作输入（在当前上下文中执行，不发给外部进程）：

[角色] agents/对应角色.md（完整正文已读取，严格按其规则工作）
[任务] 本轮任务、Mode、输入文件绝对路径、前序角色的结构化结果、真实项目路径、期望输出

执行要求：
- 只按角色定义产出结构化结果；角色步骤需要而尚未读取的资料先读取再使用，不凭主会话记忆代替。

不要写成“调用名为 `prd-entity-flow-extractor` 的 agent”。正确做法始终是：完整读取 `agents/prd-entity-flow-extractor.md`（及本轮涉及的其他角色文件），在当前上下文按该角色规则串行执行并保留中间结果。

## Result Quality Bar

最终输出必须同时满足：
- 一级标题只有 6 个，且顺序正确；章节外只允许文末“待确认与需求冲突”段
- 涉及状态对象时，每个实体状态机使用独立二级标题与独立 `stateDiagram`，图后紧跟关键补充说明；实体间联动触发按链路分段成图
- ER图章节只有图，不带额外说明文字
- ER图中的每个实体都必须展示实体名称和核心字段
- 增量SQL章节先给 MySQL SQL 代码；代码块后必须紧跟二级段落 `流程引擎实体与状态机实现边界`，除此之外不附加说明；新增/变更表只保留主键，不夹带外键、唯一键或其他索引（若调用方另行要求 DB 级唯一/幂等兜底，按调用方确认后在“待确认与需求冲突”段记录）
- `流程引擎实体与状态机实现边界` 覆盖全部有状态实体，并明确审批开启/关闭、流程实例创建、流程回调交接、纯状态机、联动投影与外部复用边界；不得把普通业务状态对象误写为流程实例
- 增量SQL中每张表有表级 COMMENT，每个业务字段有列级 COMMENT（主键与审计字段除外）
- 每个关键 PRD/既有文档动作都能在接口清单或流程图中找到映射；无法映射或存在冲突的进入“待确认与需求冲突”段
- 每个新增实体都能在 ER 图和增量 SQL 中对应起来
- 对于项目中已存在的模块/实体/表/接口/字典，必须明确标注复用关系，避免误写为新增
- 增量字典只列实际使用字典的实体字段，字典类型限定为常量/全局/自定义，单据状态原则上归为常量字典
- 增量字典的每个字段都写明所用字典编码；每个字典编码有且只有一个三级标题和一张字典项表，表格列为 `字典项编码 | 字典项名称 | 说明`
- 使用清单中的每个字典编码都能在“字典枚举项”段找到对应表格，且不存在未被任何字段引用的孤儿字典表
- 接口清单不出现前端函数名
- 接口请求参数与响应参数均为表格（同构接口用公共参数表亦可）；关键写接口写明权限/数据范围、校验、状态前提、事务/幂等、性能上限及最小正反测试依据
- 数据流转图明确模块归属与依赖方向，不建议 `common -> application`、`service -> service`、Bean 双向依赖、自注入或 `@Lazy` 掩盖环
- 列表接口有分页和 pageSize 上限；批量、导入导出、统计及外部调用有上限、异步或超时策略，不出现无界查询和循环查库设计
- 业务流程图、数据流转图都按流程/链路分段展示；每个状态机以二级标题独立成图并带图后说明，联动图独立成图
- 增量字典包含且仅包含“实体字段字典使用清单”（逐字段标注字典编码）与“字典枚举项”（每个字典编码一张表）两类内容
- 同一业务事实只用一个状态字段，不存在取值一一对应的同义双状态字段
- 状态机图中的过程叙述节点已在图后说明标注“不落库”并说明推导来源
- 新增状态/终态已写明触发方、时间字段、不可逆性与进入后必须拒绝的接口
- 需求方给出的口径变更已在 ER、SQL 注释、状态机、数据流转图、接口、字典六处同步，并在冲突/采用口径段记录依据
- 交付前 Mermaid 校验失败数为 0（配置 `MMDC_PATH` 时为真实渲染，否则为 `scripts/check-mermaid.py` 内置结构化 lint 并在答复中说明未做真实渲染），且状态机标题层级、图后说明、字典编码映射、重复状态字段、悬空章节引用、非 MySQL 方言均已由 `scripts/check-doc.py` 自检通过
- 全文无背景复述、通用技术常识和章节总结；普通说明不超过 3 句，结构化内容优先表格，重复约束只定义一次
- 接口风格看起来像来自当前仓库，而不是通用脚手架
- 字典枚举与 SQL 注释、接口、状态机用词一致

## Failure Mode

若缺少信息或依赖，不要脑补，按降级处理：
- 本地脚本不可运行（无 Python / 无 uv 且无降级可用 / 无 mysql 客户端）：降级为人工检查，在答复与“待确认与需求冲突”段说明未执行该项机器自检。纯标准库脚本（check-doc / check-mermaid）无 uv 也可直接 `python` 运行。
- `.agents/.env` 缺少 `DB_*`：跳过真实库核对，SQL 照常输出并注明“未连接真实库核对 schema”；缺少 `MMDC_PATH`：`check-mermaid.py` 使用内置结构化 lint 并说明未做真实渲染。需要环境信息时先提示用户输入，由主调用方写入 `.agents/.env`，用户拒绝则按降级处理。
- PRD 与原型都缺失（或 Mode B/C 缺既有文档）：先提示用户提供，不要直接生成；只有 PRD 或只有原型时正常执行，缺失侧信息标“待确认”并归集文末。
- 缺少前后端项目地址：不阻塞执行，输出建议稿并在待确认段说明。
- 命中 Design Readiness Gate 的 `BLOCK` 条件：停止生成确定性接口、ER 和 SQL，列出问题、影响与责任方/所需输入。
- 仅非核心信息不确定：按 `CONDITIONAL` 继续，在对应位置标“待确认”并归集文末，不硬造真实表名、权限码、字典码或模块路径。
- 任何情况下都只输出 MySQL SQL，不生成或讨论其他数据库方言。
