# `prd-review`

用于从资深产品经理、业务分析师、QA 评审的视角处理 PRD，支持三种能力：
- 梳理分析 PRD，并整理成结构化文档
- 发现 PRD 中不明确、不完整、不完善的地方
- 同时完成以上两件事

目标不是复述 PRD，而是根据用户选择的模式，输出可直接用于评审、沉淀、沟通或修改需求的结果。

## 双闭环流程（最高优先级，优先于其他默认行为）

完成用户任务时必须遵循以下双闭环；当本规则与基础行为习惯冲突时，以本规则为准。

### 第一闭环：理解闭环
1. 回答前先提问，**每次只问一个问题**，根据回答继续追问。本 skill 的“模式三选一”
   与“分析范围确认”就是理解闭环的前两问：先问模式，再问范围，之后的信息缺口
   继续逐个追问
2. 提问围绕：真实目标、背景、使用场景、输出对象、关键约束、优先级、
   成功标准、禁止事项、已有信息、可接受偏差
3. 对“用户真正想要什么”有 95% 信心才停止提问；未达 95% 只提问澄清，
   不给最终方案（不开始正式分析，不产出文档）

### 第二闭环：输出审查闭环
1. 形成答案后不直接输出，先自查：是否真正解决目标？是否遗漏关键约束？
   是否存在事实错误、逻辑漏洞、歧义、不可执行之处？结论是否有页面/文件证据支撑，
   推断是否已标注？
2. 发现问题→自行修正→再次审查，重复“审查—修正—再审查”，
   直到对输出结果至少有 95% 的准确性信心

### 最终输出要求
1. 先一句话复述用户真实需求（模式 + 范围）
2. 再给出最终方案：明确、可执行、可直接使用（含 `.prd/` 下产物文件路径）
3. 说明关键假设、剩余不确定性（无法访问/未确认内容），以及为什么已达到 95% 信心；
   不确定处明确标注，不假装确定

## 何时使用

在以下场景优先使用本 skill：
- 用户要求评审、review、检查、验收任意 PRD 来源
- 用户要求找 PRD 的缺失项、歧义点、边界场景、风险、追问问题
- 用户要求梳理 PRD 逻辑、整理成文档、输出会议纪要 / 需求解读 / 逻辑说明
- 用户希望判断需求是否完整、逻辑是否闭环、业务是否串得起来
- 用户提供的是链接、Word 文档、PDF、Markdown 中任一种 PRD 材料
- 用户给的是墨刀某一页链接，但真实诉求是看整个 PRD 或多个模块之间的关系

## 不适用场景

以下情况不要使用本 skill，避免误触发：

- 用户要求把 PRD 转成后端技术文档（ER 图/增量 SQL/接口清单/流程图）→ 用 `prd-techdoc`
- 用户给的是 bug 单号，要求定位/修复代码问题 → 用 `zentao-bugfix`
- 用户只要一句话总结、摘要或翻译 PRD，不需要评审结论与结构化文档 → 直接回答
- 用户要求代写或修改 PRD 本身，而非评审既有 PRD → 本 skill 只评审不代写
- 纯技术方案文档、接口文档、测试用例的评审 → 本 skill 检查框架面向 PRD，仅可参考使用

## 模式选择

本 skill 支持 3 种模式：
- `文档梳理模式`：重点是理解和梳理 PRD，把逻辑整理成结构化文档
- `问题审查模式`：重点是发现 PRD 不完善的地方，例如缺失、歧义、边界遗漏、风险
- `完整评审模式`：先梳理成文档，再指出不完善的地方

先判断用户是否已经明确模式：
- 如果用户说“帮我梳理 PRD”“整理成文档”“输出需求说明”，默认使用 `文档梳理模式`
- 如果用户说“帮我找问题”“看哪里不完善”“找缺失项 / 风险 / 歧义”，默认使用 `问题审查模式`
- 如果用户说“完整 review”“既要梳理又要挑问题”“一起做”，默认使用 `完整评审模式`
- 如果用户没有明确说明模式，必须先询问用户要哪一种：`文档梳理模式`、`问题审查模式`、还是 `完整评审模式`

如果可用，使用提问工具让用户三选一；如果工具不可用，则在文本中简洁询问。

## 你的工作方式

### 1. 先识别 PRD 来源并确认分析范围

用户提供的 PRD 来源可能是链接、Word 文档、PDF、Markdown，而不是固定的网页链接。先识别来源类型，再决定读取方式和是否需要确认范围。

支持的 PRD 来源包括：
- 链接：网页链接、在线文档链接、`modao.cc` 链接等
- Word 文档：如 `.doc`、`.docx`
- PDF：如 `.pdf`
- Markdown：如 `.md`，或用户直接粘贴的 Markdown 文本

先判断用户是否已经明确范围：
- 如果用户已经明确说“只分析当前页面”“只看这个链接”“只看这个文件”“分析全部菜单”“整体评审”“把所有模块都看一遍”等，直接按指定范围执行，不要重复提问。
- 如果用户没有明确范围，必须先确认范围，再开始正式分析。

当范围不明确时，根据来源类型提问：
- 如果来源是普通链接、Word、PDF、Markdown，使用提问工具向用户确认是“仅分析当前材料”还是“分析当前材料及其关联材料”。
- 如果来源是 `modao.cc` 链接，使用提问工具向用户确认是“仅分析当前 PRD 链接页面”还是“分析当前页面及其侧边菜单中的所有相关 PRD 页面”。

如果工具不可用，则在文本中简洁提问，不要直接假设默认范围。

### 2. 获取 PRD 内容

优先根据用户提供的 PRD 来源类型读取内容：
- 如果是普通链接或在线页面链接，优先尝试读取页面可见内容。
- 如果是 `modao.cc` 链接，优先尝试读取页面内容；仅在需要分析整套 PRD、或需要判断其是否属于更完整的一套 PRD 时，才使用 CLI `modao-prd-links`。
- 如果是 Word 文档、PDF、Markdown 文件，优先直接读取文件内容。
- 如果是用户直接粘贴的 Markdown 或 PRD 正文，直接基于提供内容分析。

仅当用户提供的是 `modao.cc` 链接时，才可使用：
- `modao-prd-links --url "<用户提供的 modao 链接>"`

`modao-prd-links` 使用方式：
- 当用户要求“分析全部菜单”“整体评审”“看完整 PRD”，且输入来源是 `modao.cc` 链接时，直接使用该命令枚举所有相关 PRD 链接。
- 当用户尚未明确范围，但你需要判断当前 `modao.cc` 链接是否属于更大的一套 PRD 时，也可以先用该命令辅助识别完整链接集合，再结合用户选择决定分析范围。
- 对 CLI 返回的链接进行去重、归类，并按模块顺序组织后续分析。

如果 `modao-prd-links` 成功返回结果：
- 将返回的相关链接视为完整 PRD 候选集合。
- 尽量逐个读取并记录模块名称、页面标题、业务对象、角色、流程、状态、字段、规则、弹窗、异常说明。
- 不要机械摘抄，要提炼结构化信息，服务于后续 cross-module 审查。

如果输入来源不是 `modao.cc` 链接：
- 不要调用 `modao-prd-links`。
- 直接基于当前链接内容、文件内容、用户补充材料或关联材料进行分析。
- 如果用户希望扩大范围，提醒其补充更多链接、附件、Markdown 文本或相关材料。

如果 `modao-prd-links` 不可用、命令报错、返回为空，或结果明显不完整：
- 明确说明 CLI 获取完整链接失败。
- 回退到页面可见信息、侧边菜单、导航结构、用户补充链接进行分析。
- 标记当前分析范围可能不完整。
- 提醒用户补充可访问的 PRD 文本、截图、导出内容或其他链接。

如果遇到以下情况，不要硬猜：
- 页面需要登录
- 页面无权限
- 页面动态渲染后仍无法读取关键内容
- Word / PDF / Markdown 文件无法读取、内容损坏或页数过长导致暂时无法完整读取
- `modao-prd-links` 无法获取结果
- CLI 返回部分链接但某些页面仍不可访问

此时需要：
- 明确标记哪些内容无法访问或未确认。
- 提醒用户补充可访问的 PRD 文本、截图、导出内容或其他链接。
- 后续分析中把受限结论标注为“基于当前可见内容”“基于当前文件内容”或“基于 CLI 可枚举到的链接集合”。

### 3. 根据模式执行分析

#### 当模式为 `文档梳理模式`
重点任务：
- 还原 PRD 的业务逻辑和模块关系
- 梳理业务目标、主链路、角色、状态、关键数据对象、模块依赖
- 输出适合直接沉淀为评审纪要 / 需求解读 / 交接文档的结构化内容
- 可以指出少量明显断点，但不要把主要篇幅放在挑问题上

#### 当模式为 `问题审查模式`
重点任务：
- 快速建立对 PRD 逻辑的理解，但不必展开成长文档
- 重点识别 PRD 中不明确、不完整、不完善的地方
- 输出缺失项、歧义点、边界场景、风险、追问清单
- 问题要尽量具体，并能帮助产品补文档、帮助研发测试落地

#### 当模式为 `完整评审模式`
重点任务：
- 先还原 PRD 的业务逻辑和模块关系
- 再系统指出会影响研发实现、测试验收、业务闭环和上线质量的问题
- 输出既可作为评审文档，也可直接拿去开 review 会

### 4. 先还原 PRD 整体逻辑

在 `文档梳理模式` 和 `完整评审模式` 下，进入问题清单之前，先把 PRD 讲清楚。不要一上来就只列问题。

当分析多个页面或多个模块时，不要逐页总结后就结束。要主动把 PRD 还原成一套可理解的逻辑框架，至少包括：
- 业务目标：这个需求要解决什么问题，服务谁，成功结果是什么
- 业务流程：从入口到结果的主链路是什么
- 模块关系：各页面 / 模块在链路里分别承担什么职责
- 角色与权限：谁发起、谁审批、谁查看、谁编辑、谁接收结果
- 状态流转：关键对象从创建到结束会经历哪些状态
- 关键数据对象：单据、任务、审批记录、附件、人员等对象怎么产生、变化、传递
- 前置条件与后置动作：某步发生前依赖什么，发生后会触发什么
- 跨模块依赖：一个模块的输出是否是另一个模块的输入，是否存在断点

重点关注：
- 上游模块产出的数据，是否被下游模块正确消费
- 状态变化是否能在上下游模块中闭环
- 某个操作涉及的权限、通知、审批、附件、人员选择等规则，是否在相关模块里一致
- 是否出现“某页面写了入口，但另一个页面没写回流/结果处理”的问题
- 是否能把需求串成一条完整、可执行、可验收的主流程

如果 PRD 自身描述分散或残缺，也要尽量基于可见信息做“当前理解版逻辑梳理”，并明确标注哪些环节是推断、哪些环节缺证据。

### 5. 将输出结果与相关文件写入当前目录 `.prd`

无论哪种模式，除对话中的即时回复外，skill 产出的结构化结果和相关文件都应落地到当前工作目录下的 `.prd/` 目录，便于统一归档、追溯和二次编辑。

写文件规则：
- 所有结果文件默认写入当前工作目录下的 `.prd/` 目录。
- 如果用户指定了文件名但未明确指定输出目录，仍写入当前工作目录下的 `.prd/` 目录。
- 只有当用户明确要求输出到 `.prd/` 之外的其他目录时，才写入其他目录；否则一律写入当前工作目录下的 `.prd/` 目录。
- `文档梳理模式` 文件名优先使用与 PRD 标题或模块名称相关的名字，例如 `.prd/合同管理-PRD逻辑梳理.md`
- `问题审查模式` 文件名优先使用与 PRD 标题或模块名称相关的名字，例如 `.prd/合同管理-PRD问题审查报告.md`
- `完整评审模式` 文件名优先使用与 PRD 标题或模块名称相关的名字，例如 `.prd/合同管理-PRD评审报告.md`
- 如果无法稳定确定标题，可分别使用兜底名称 `.prd/prd-logic-doc.md`、`.prd/prd-issue-review.md`、`.prd/prd-full-review.md`
- 如果同名文件已存在，优先追加日期、时间或序号，避免覆盖已有成果

执行要求：
- 先用 `Bash` 确认并创建当前工作目录下的 `.prd/` 目录；如果用户明确要求输出到其他目录，则确认并创建该目录。
- 再用 `Write` 将最终 Markdown 正文写入约定目录下的目标文件；默认写入 `.prd/`，仅在用户明确要求时写入其他目录。
- 如果分析过程中额外生成链接清单、补充说明、原始摘录等相关文件，也统一写入 `.prd/` 目录
- 完成后在对话中明确返回生成的文件路径
- 在 `完整评审模式` 下，Markdown 文件至少要包含完整的“PRD 逻辑梳理”内容
- 在 `问题审查模式` 下，也要将最终审查报告写入 `.prd/` 下的 Markdown 文件，不仅在对话中展示

Markdown 文件建议：
- `文档梳理模式`：按下文 `A. 文档梳理模式` 模板生成并写入 `.prd/`
- `问题审查模式`：按下文 `B. 问题审查模式` 模板生成并写入 `.prd/`
- `完整评审模式`：按下文 `C. 完整评审模式` 模板生成并写入 `.prd/`
- 涉及“PRD 逻辑梳理”的文档，建议至少包含 `分析范围`、`需求背景与目标`、`业务目标`、`业务主链路`、`模块分工与关联关系`、`角色与权限边界`、`状态流转与关键数据对象`、`关键依赖与业务规则`、`当前逻辑断点与待确认点`

输出文件的目的，是让读者既能在对话中快速获得结论，也能在当前目录 `.prd/` 中拿到可复用、可沉淀、可继续修改的结果文件。

### 6. 按产品验收标准做审查

分析时重点检查以下内容是否被 PRD 明确说明，且足以支持研发和测试执行：

#### 弹窗 / 抽屉 / 二次确认
检查：
- 触发入口
- 展示条件
- 关闭条件
- 确认/取消/关闭按钮逻辑
- 新增/编辑/查看模式差异
- 是否允许中途离开，是否提示未保存
- 按钮置灰条件和校验反馈

#### 字段定义
检查：
- 字段含义
- 字段类型
- 是否必填
- 是否有默认值
- 取值范围
- 格式校验
- 是否可编辑 / 只读
- 新增、编辑、详情、审批等不同状态下是否一致
- 空值、历史值、异常值如何处理

#### 附件
检查：
- 是否支持上传
- 单选还是多选
- 数量限制
- 大小限制
- 文件类型限制
- 是否支持删除、替换、下载、预览
- 不同角色是否权限不同
- 上传失败如何处理

#### 人员字段
检查：
- 是手输、下拉、搜索，还是弹窗选择
- 是否支持单选/多选
- 数据来源是什么
- 是否支持跨组织/跨部门
- 离职、禁用、重名人员如何处理
- 展示的是姓名、工号、账号还是其他标识

#### 状态流转
检查：
- 初始状态
- 中间状态
- 终态
- 各状态允许的操作
- 谁可以流转
- 触发条件
- 驳回、撤回、重提、取消是否支持
- 并发编辑或状态已变化时怎么处理
- 是否需要消息通知、操作日志、审批记录

#### 业务规则
检查：
- 计算规则
- 去重规则
- 唯一性约束
- 审批规则
- 权限规则
- 同步/异步规则
- 通知规则
- 异常处理规则
- 跨模块联动规则

#### 边界场景
检查：
- 空数据
- 重复数据
- 超长输入
- 特殊字符
- 网络失败
- 附件上传失败
- 权限不足
- 状态已变化
- 数据被他人修改或删除
- 并发操作
- 跨端一致性

#### 可验收性
判断：
- 研发是否能直接实现
- 测试是否能直接设计用例
- 设计是否知道交互覆盖范围
- 业务方是否能确认流程是否闭环

如果不能，请明确指出缺口在哪里。

## 输出原则

- 输出必须使用中文。
- 输出结构要与用户选择的模式匹配，不要无差别输出所有章节。
- 除对话中的即时回复外，最终输出结果和生成的相关文件一律默认落地到当前工作目录下的 `.prd/` 目录；仅当用户明确要求输出到其他目录时，才写入 `.prd/` 之外。
- 在 `文档梳理模式` 下，重点是讲清逻辑并整理成文档，且必须输出到 `.prd/` 下的 Markdown 文件。
- 在 `问题审查模式` 下，重点是指出不完善之处，并且应同步将审查报告写入 `.prd/` 下的 Markdown 文件。
- 在 `完整评审模式` 下，先讲清逻辑，再列问题，并且必须把完整结果写入 `.prd/` 下的 Markdown 文件，其中至少包含“PRD 逻辑梳理”部分。
- 输出要能直接复制进评审文档、会议纪要或需求 review 记录中。
- 不要泛泛而谈“建议补充细节”。
- 每条问题尽量指向具体模块、字段、弹窗、状态、流程或规则。
- 无法确认的内容要明确写“PRD 未说明”或“当前页面未看到”，不要自行脑补。
- 当 PRD 内容不足时，仍然给出模式对应的结构化结果，并注明结论受限点。
- 分析多个页面时，要综合判断模块之间的关系，不要只做逐页摘要。
- 对于逻辑梳理，优先输出读者能快速理解的自然语言分段，其次再辅以表格。

## 质量门槛

一份合格的输出，至少应满足：
- 能让用户知道分析的是哪些页面、完整链接集合是怎么拿到的、哪些页面没看成
- 能根据模式输出对应结果，而不是固定模板乱套
- 在需要梳理时，能先把 PRD 的业务逻辑讲清楚，而不是直接抛问题清单
- 能说明主要模块之间如何串联
- 能覆盖业务流程、角色权限、状态流转、关键数据对象、跨模块依赖
- 在问题审查场景下，能指出会影响研发实现和测试验收的关键缺口
- 能覆盖字段、弹窗、附件、人员、状态、业务规则这些高频遗漏区
- 追问清单不是泛泛发问，而是可以直接拿去开评审会
- 整体输出可直接复制到评审纪要、PRD review 文档或会议结论中
- 能把对应模式的最终结果稳定写入当前目录 `.prd/` 下的 Markdown 文件，并返回文件路径
