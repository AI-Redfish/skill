# 周报格式与整理规范

本文件定义 weekly-report 产出的周报结构与整理规则。生成周报时必须遵循本模板。

## 周报 Markdown 模板

```markdown
# 本周工作周报（基于 Git 提交记录）

**数据来源**：仓库 <repo 名>；窗口 <窗口描述（如"最近 5 个工作日：MM-DD ~ MM-DD"）>；
作者 <邮箱>；本周提交 <commit_total> 个（非合并 <non_merge_total> 个），
变更 <files_changed> 个文件次，+<insertions> / -<deletions> 行；修复 Bug <N> 个。

---

## 本周工作总结

### 一、<模块/主题名 1>
- <一条工作内容：动词开头，含做了什么+结果/影响；有 Bug 编号则附上>
- ...

### 二、<模块/主题名 2>
- ...

（模块数量按实际分组，建议 2~4 个；不足 2 个模块时可平铺为列表）

## 进行中的修改（未提交）

- <worktree 路径或分支名>：<N> 个未提交文件，例如 <代表性文件 1~3 个>
（无未提交修改时写"无"，并省略本节上方的空行说明）

## 下周计划（拟定）

1. <依据未推送/未合入提交与未提交修改推断的事项>
2. <跟进评审/测试/合入等常规后续>

---

**说明**：
- 下周计划为 AI 推断的拟定内容，可自行调整
- <其他需要说明的口径，如"某 worktree 本窗口内无提交">
```

## 整理规则

1. **分组原则**：按业务模块/主题分组（依据提交 subject、bug_ids 与改动文件路径），
   同主题的 feature 与其衍生 bugfix 归入同组；组内按时间倒序或"功能→修复"排序。
2. **内容来源**：优先使用 commit subject 原文意译；subject 过于含糊
   （如只有"冲突解决""修复问题"）时，执行 `git show <hash> --stat` 看改动文件，
   必要时看关键文件 diff，用一句话补充"改了什么模块+解决什么问题"。
3. **Bug 编号**：subject 中 `#\d+` 视为禅道 Bug 编号，必须保留在对应条目中；
   统计区汇总去重后的 Bug 总数。`fixup!`/`squash!` 开头的提交并入其目标提交
   的条目，不单独成条。
4. **提交状态提示**：`pushed=false` 的提交在数据来源行注明"含未推送提交"；
   `in_dev=false` 且 `pushed=true` 注明"部分提交未合入 dev"。
5. **进行中修改**：数据中 `uncommitted_count > 0` 的 worktree 必须列入"进行中的修改"，
   这部分不计入提交统计；该 worktree 带有 `uncommitted_note` 降级标注时，
   在条目后括注说明
6. **数量口径**：统计只计非 merge 提交；merge 提交总数 = commit_total - non_merge_total，
   可在数据来源行括注。
7. **多 worktree 无提交**：某 worktree 窗口内无该作者提交时不单独列条目，
   可在末尾说明区一句话带过。
8. **简洁优先**：每条内容一句话，不超过 40 字；总条目数控制在 12 条以内，
   超出时合并同主题条目。
9. **防幻觉**：只依据脚本 JSON 数据与 git 查询结果整理；数据中没有的信息
   （如提交原因、需求背景）不编造，不确定的表述用"推断""拟定"标注。
