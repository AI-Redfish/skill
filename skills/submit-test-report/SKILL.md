# `submit-test-report` — 提测报告（提测确认接收单）生成

根据**项目分支代码 + 需求文档 + 技术方案文档**，套用固定模板生成《需求提测确认接收单》。

三条铁律：
1. **格式与模板一模一样**：只允许改文件名和替换关键字段文本，版式、表格结构、勾选样式一概不动。一律通过 `scripts/generate_report.py` 生成，禁止手写 docx。
2. **不臆造**：字段值必须来自需求文档、技术方案文档、代码（git log/diff）或用户确认；推断值要明确标注并请用户确认。
3. **不确定先问**：必要信息缺失或冲突时，按“理解闭环”先提问再生成。

**输出位置（默认桌面）**：不指定 `--out` 时，生成文件默认写到**当前用户桌面**（脚本优先读注册表 `User Shell Folders\Desktop`，兼容 OneDrive 重定向，取不到时回退当前目录）；用户明确指定输出目录时以用户为准。

## 变更明细写作规范（产品功能视角，最高优先级）

第四节「需求变更明细」的**变更摘要、影响模块/页面、验证要点**三列，以及「自测范围说明」，必须站在**产品功能/用户使用**的角度描述，读者是测试与产品同学：

- ✅ 写：菜单路径/页面名（如“设备 > 组态图配置 - 图纸属性面板”）、用户操作、系统行为与规则、空态/提示/边界、对存量数据的影响
- ❌ 禁止出现：接口 URL 与接口名、类名/方法名/文件名、数据库表名/字段名、请求参数与取值（如某参数传某值）、事务/拦截器/DTO 等代码术语
- 变更摘要一句话说清“哪个功能，用户能做什么/行为有什么变化”；验证要点写成测试人员可直接执行检查的预期结果（含正常路径＋边界＋提示）
- 技术实现细节（接口改造点、表结构、参数设计）留在技术方案文档，不在提测单重复；「底层/公共变更」表可写数据库调整等技术变更，但其「影响范围与回归建议」列仍用功能语言描述

## 目录结构

```
submit-test-report/
├── SKILL.md                          # 本文件
├── assets/
│   └── 需求提测确认接收单-模板.docx    # 唯一格式基准（源自桌面参考文档，勿改）
└── scripts/
    ├── generate_report.py            # 生成器：模板 + fields.json → docx（含 md/docx 附录转换）
    ├── read_docx.py                  # 读取 .docx 文档内容（需求/技术方案为 docx 时用）
    └── fields.example.json           # fields.json 完整示例
```

## 何时使用 / 不使用

使用：用户要求"生成提测报告 / 提测单 / 提测确认接收单 / 填提测单 / 提交测试给测试组"。
不用：评审 PRD（`prd-review`）、PRD 转技术文档（`prd-techdoc`）、修 bug（`zentao-bugfix`）；仅"看看提测单怎么填"这类咨询直接回答。

## 双闭环流程（最高优先级）

### 第一闭环：理解闭环 —— 收集必要信息
必要信息清单（✱ = 缺失即阻塞，必须问；其余可给默认值待确认）：

| 类别 | 信息 | 缺失时的处理 |
|---|---|---|
| 代码 | ✱后端代码仓库路径 + ✱分支名 | 询问；顺带问基线（对比基准分支/版本） |
| 代码 | ✱前端代码仓库路径 + ✱分支名 | 询问；纯后端需求可明确说"不涉及" |
| 文档 | ✱需求文档（路径/链接） | 询问 |
| 文档 | ✱技术方案文档（路径/链接） | 询问 |
| 版本 | 提测版本号、基线版本号 | 先从分支名/文档/近期 tag 推断，推断不出则问 |
| 人员 | 开发负责人、产品经理、项目经理、测试接收人、参与人员 | 先从两份文档/git log 作者推断，再列给用户确认 |
| 时间 | 提测时间、期望测试起止 | 默认：提测=今天，开始=明天，结束=—；列给用户确认 |
| 测试 | 测试阶段（冒烟/功能/回归/联调/线上验收/IPD/其他） | 默认"冒烟+功能"，列给用户确认 |
| 资料 | 需求/原型文档：**链接**（gitlab 等可访问地址）；系统分析/设计、技术方案/接口：**本地文件路径**（转换为附录嵌入 docx 末尾） | 链接填 http/https；路径不存在报错；某类无文档时填“无：<原因>” |

提问规则：
1. 能从材料推断的先推断，**不要逐项连环追问**；只有 ✱ 阻塞项缺失或推断互相矛盾时才提问。
2. 提问合并为一轮，分点列出，每个问题给出推断的默认值让用户确认或纠正。
3. 使用 AskUserQuestion 工具（不可用则在文本中简洁列出）。

### 第二闭环：输出审查闭环
生成后必须自查，未达 95% 信心不交付：
1. 用 `--dump` 重读生成的 docx，逐项核对第二闭环清单，并额外检查：
   - 变更明细/自测范围**无任何接口、类名、表名、参数等代码元素**（搜索 `.java`、URL、表名等关键词复查）；
   - 第六节：需求/原型行是可访问链接（http/https）；设计/技术行为“见附录（已嵌入本文档末尾）…”；附录标题与表格已生成（--dump 可见正文 8 表之后的附录表格与附录一/二标题）；
   - 必填项无留空、变更条数与文档/代码一致、日期格式 YYYY-MM-DD、勾选位置正确。
2. 核对变更明细的每一条都能在需求文档/技术方案/代码提交中找到出处。
3. 脚本已保证除 `word/document.xml` 外所有部件与模板逐字节一致；若用户反馈格式问题，先怀疑模板被改动，重新核对 `assets/` 下模板。

## 工作步骤

### Step 1 收集并读取材料
- 需求文档/技术方案文档：`.md` 直接 Read；`.docx` 用 `python scripts/read_docx.py 文件.docx`；在线链接则抓取正文。
- 记录素材出处（哪个文档哪一节），供变更明细溯源。

### Step 2 分析分支代码（前后端分别做）
```bash
git -C <仓库路径> fetch origin '<分支>' && git -C <仓库路径> log --oneline origin/<基线分支或tag>..origin/<提测分支>
git -C <仓库路径> diff --stat origin/<基线>..origin/<提测分支>
```
- 用提交与 diff 核对变更范围，补充/修正从文档提取的变更明细。
- 公共组件、壳程序、协议/配置框架、工具库等**跨模块或无需求号**的改动 → 归入"底层/公共变更"表，并写明影响面与连带回归范围。
- 从改动目录判断涉及端（PC/App/硬件），判断不了就问。

### Step 3 汇总字段并确认
- 按下方 schema 写 `fields.json`（UTF-8）。
- 把所有推断值（版本号、人员、时间、测试阶段、涉及端、资料链接、变更明细摘要）列表给用户过目；用户确认或修正后才生成。阻塞项缺失则按理解闭环提问。

### Step 4 生成
```bash
python <skill目录>/scripts/generate_report.py --fields fields.json          # 默认输出到桌面
python <skill目录>/scripts/generate_report.py --fields fields.json --out "<目录>/需求提测确认接收单-<迭代名称>.docx"  # 用户指定目录时
```
- 默认输出：当前用户桌面，文件名 `需求提测确认接收单-{iteration}.docx`；用户指定目录则优先。
- **第六节资料策略**：需求/原型文档为链接（单元格直接展示 URL，需确保可访问）；系统分析/设计与技术方案/接口文档由脚本把**文档内容转换为附录**，分页追加在“八、备注”之后（附录一/附录二…），正文模板部分一字不动；docx 单元格写“见附录（已嵌入本文档末尾）：文件名”。
- 背景说明：WPS 个人版 COM 的 AddOLEObject 不可用（E_FAIL），OLE 图标嵌入在本环境不可靠，附录方式更可靠且测试直接可读，无需额外文件。
- 交付时告知：docx 路径、已嵌入的附录清单、需求/原型链接。

### Step 5 自查并交付
1. `python scripts/generate_report.py --dump <输出文件>` 核对第二闭环清单。
2. 交付时说明：输出路径、变更条数、推断并已被确认的字段、剩余不确定项（如有）。

## fields.json schema

```jsonc
{
  "iteration": "需求号/迭代名称（必填，也用于文件名）",
  "basic": {
    "test_version": "提测版本号，如 V6.0.8.1",
    "baseline_version": "基线版本号，如 V6.0.7.4（脚本自动补充说明后缀）",
    "submit_date": "提测时间 YYYY-MM-DD",
    "expect_start": "期望测试开始时间 YYYY-MM-DD",
    "expect_end": "期望测试结束时间，无则 —"
  },
  "roles": {
    "dev_owner": "开发负责人", "product_manager": "产品经理",
    "project_manager": "研发项目经理，可空串",
    "test_owner": "测试接收人/测试责任人", "participants": "参与人员，顿号分隔"
  },
  "test_stages": ["冒烟测试", "功能测试"],  // 从7个固定选项中多选；脚本把选中项 ☐ 改 ☑
  "env": { "apps": "PC、App", "hardware": "—", "min_runtime": "—" },
  "changes": [                              // 第四节：需求变更明细，每条一行
    { "req_no": "需求号，同迭代可空串",
      "type": "新增|优化|修复|重构/底层变更",
      "summary": "变更摘要（一句话）",
      "modules": ["影响模块/页面，每项一段", "可多段"],
      "verification": "验证要点（开发自测已覆盖）" }
  ],
  "common_changes": [                       // 第四节：底层/公共变更，无则留空数组（保持模板空表）
    { "item": "项目", "description": "变更说明", "impact": "影响范围与回归建议" }
  ],
  "self_test": {
    "conclusion": "通过 | 有条件通过 | 未完成",   // 脚本勾选对应项，未完成不得提测
    "scope": "自测范围说明（功能视角，规则同变更明细）"
  },
  "docs": {                                 // 第六节：requirement 填链接（可数组放多个）；design/tech 填本地文件路径（md/docx/txt，
                                            // 转换为附录嵌入 docx 末尾）；无文档填“无：<原因>”，禁止留空；设计/技术不支持链接
    "requirement": "需求PRD/原型文档的 gitlab 等链接",
    "design": "系统分析/设计文档的本地路径",
    "tech": "技术方案/接口文档的本地路径"
  }
}
```

模板中“七、测试确认”（测试结论/回退原因/责任人/日期）由测试责任人填写，**保持模板原样不填**；“八、备注”同样留空。

## 从材料到“产品功能视角”的转换方法

技术文档/代码 diff 里的接口、字段、表结构，翻译成功能语言再填入提测单：

| 技术材料中的表述 | 提测单中应写成 |
|---|---|
| 改造 /listCurSystemScaleImage，新增 campusIds 参数 | 图形展示支持按所属院区筛选，只显示所选院区范围内的图纸 |
| scale_image 新增 sort_order 字段，服务端内存排序 | 图纸支持配置展示排序，列表按排序值升序展示 |
| upsert 校验 sortOrder 0~99999999999、component=0 拒绝 | 排序最多 11 位数字，超出或填非数字时无法保存并提示；组件类型图纸不涉及该属性 |
| 复用 getUserCampusList 做权限过滤 | 下拉只能选择当前登录用户有权限院区范围内的图纸 |

写完后自查一遍：测试同学不看技术文档，能否仅凭这三个列就理解改了什么、去哪些页面、怎么验证。

## 注意事项

- 模板路径默认取 `<skill目录>/assets/需求提测确认接收单-模板.docx`，仅当用户明确指定其他模板时才用 `--template` 覆盖。
- 输出位置：省略 `--out` 时脚本自动写桌面（读取注册表 Desktop，兼容 OneDrive 重定向，失败回退当前目录）；交付时告知用户桌面上的完整文件名。
- docs 策略由脚本强制：requirement 传本地路径报错（应填链接）；design/tech 传链接报错（应填本地路径以转附录）；留空报错（除非“无：<原因>”）。
- 所有字符串写入前会清洗换行为空格；多段内容（如 modules）用数组表达。
- 脚本报错"未找到 XX 表/行"说明模板被改动过：先 `--dump assets/需求提测确认接收单-模板.docx` 核对结构，再决定修复脚本或恢复模板，不要带病生成。
